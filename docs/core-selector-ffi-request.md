# Контракт управления selector для мобильного leastPing

Контракт согласован с владельцем BlazeCore и реализован в исходниках
`10512be664e2100bb4a0ad3bb95f6c70a184ee2d` 22 ноября 2026 года.
Доступен проверенный Android bundle для x86_64 и ARM64; клиентская TUN-приёмка
x86_64 фиксируется отдельно. Физический ARM64 и Apple SDK/link/runtime ещё
не проверены.
Изменения и сборка исходников BlazeCore выполняются его владельцем.
Текущее платформенное покрытие и результаты запуска находятся в
[отчёте приёмки](xray-balancer-acceptance.md).

## Зачем требуется контракт

Blazer сохраняет Xray-граф, наблюдения observatory, выбор leastPing и fallback.
На Windows клиент измеряет каждого наблюдаемого участника через отдельный
аутентифицированный SOCKS-слушатель того же процесса BlazeCore. Выбранный участник
меняется через локальный controller. Существующие TCP/UDP-сеансы сохраняют выход.

Для Android/iOS достаточно открыть те же фиксированные слушатели внутри
единственной сессии TUN и заменить транспорт команды выбора с HTTP на FFI.
Измерения, расписание и выбор остаются в ядре клиента; новый прокси-пересыльщик
пользовательского трафика в Blazer не нужен.

FFI запускает обычные дополнительные слушатели вместе с одним TUN:
`src/ffi/common.rs`, `start_from_source`, разделение `ResolvedConfig::Server` и
`TunServer`, затем `start_servers`. Они останавливаются вместе с TUN.
`validate_ffi_support` в `src/config/validate.rs` отклоняет controller и URL-test;
`ControlConfig::reject_ffi` находится в `src/config/types/clash_api.rs`.
В исходной ревизии `b90121c…` команды изменения named selector не было.
В согласованной реализации владелец выбора опубликован через
`src/ffi/selection.rs`, C header и JNI exports; HTTP controller в FFI не нужен.

## Минимальный API

Существующий C calling convention и тип handle сохраняются:

```c
#include <stdint.h>

#define BLAZECORE_CAP_SELECTOR_CONTROL UINT64_C(1)

uint64_t blazecore_get_capabilities(void);
int blazecore_select_outbound(long handle, const char *group, const char *member);
```

Java-контракт в существующем классе `com.blazecore.BlazeCoreNative`:

```java
public static native long getCapabilities();
public static native int selectOutbound(long handle, String group, String member);
```

JNI exports:
`Java_com_blazecore_BlazeCoreNative_getCapabilities` возвращает `jlong`,
`Java_com_blazecore_BlazeCoreNative_selectOutbound` возвращает `jint` и принимает
`jlong`, два `JString` после обычных JNI environment/class аргументов.
Новый C API нужен также в iOS/macOS packet-flow библиотеке и её заголовке.

Бит `SELECTOR_CONTROL` объявляется только при реализации этого контракта с
живым владельцем выбора. Другие биты зарезервированы. Получение capabilities
не запускает runtime, не меняет сессию и не требует инициализации логирования.
Состав capabilities вместе с проверяемой ревизией библиотеки определяет
возможность включения мобильного адаптера; совпадения строки `0.3.7` недостаточно.

| Код | Значение |
| --- | --- |
| `0` | Выбор опубликован для новых соединений |
| `-1` | Неверный аргумент: null, UTF-8, пустое/слишком длинное имя |
| `-2` | Handle не относится к живой сессии либо уже остановлен |
| `-3` | Сессия запускается; каталог ещё не опубликован |
| `-4` | Группа не существует |
| `-5` | Участник не входит в группу |
| `-6` | Тип группы не `selector` либо возможность отсутствует |
| `-7` | Управление занято; команда не применена и не поставлена в очередь |
| `-8` | Внутренняя ошибка; выбор не опубликован |

Имена заимствуются на время вызова, имеют длину 1–127 байт, не содержат
управляющих символов. API не возвращает выделенные строки, указатели на runtime,
конфигурации или секреты. Значения имён и конфигураций не включаются в сообщения
об ошибках. Это адаптер существующего контракта named selector, а не новый
балансировщик BlazeCore.

## Владение сессией и конкурентность

- Все варианты start — Android `start`/`startWithFd`, обычный C start и packet-flow
  start — должны возвращать уникальный положительный handle для каждого нового
  запуска. Возвращавшийся ранее Android и обычным start `1` заменён уникальной
  генерацией: поздняя команда старого наблюдателя не переключает следующую сессию.
  Handle не переиспользуется
  в пределах процесса. Переполнение возвращает ошибку запуска.
- После публикации готовности команда применяет выбор атомарно. Она не
  перезапускает TUN, слушатели или WireGuard и не разрывает открытые потоки и
  UDP-ассоциации. Нет сохранения выбора на диск и внешнего controller listener.
- Вызов безопасен с выделенной очереди клиента/расширения. Он не удерживает
  глобальный mutex жизненного цикла во время ожидания сетевой работы и не
  вызывается из packet-flow/protect callback: такой повторный вход получает `-7`.
  Наличие Tokio-контекста само по себе не запрещает эту неблокирующую команду;
  клиент вызывает адаптер через `spawn_blocking`, без вложенного `block_on`.
- Уточнение владельца ядра от 22 ноября: изменение выполняется немедленно в
  памяти с неблокирующим `try_lock`, без очереди команд. Если управление занято,
  возвращается `-7`, и команда не сможет примениться позднее. Изменение выбора
  и подтверждение должны быть согласованы; состояние с неизвестным результатом
  нельзя сообщать как обычный отказ «не применено». Клиент дополнительно
  ограничивает ожидание адаптера двумя секундами и отменяет свой наблюдатель.
- Stop запрещает новые команды, завершает владельца выбора
  и дополнительные слушатели перед возвратом. Поздние результаты проверок с
  прежним handle отклоняются. Новый start не наследует отчёты или выбор.
- До запуска первого наблюдения применяется начальный fallback/global default,
  уже записанный в конфигурации selector клиентом.

Общая сессия находится в `src/ffi/common.rs`; FFI-владелец в
`src/ffi/selection.rs` переиспользует существующий `SelectionOwner` и общее
состояние выбора. Тонкие C/JNI exports соответствуют `include/blazecore.h`.
Добавление полного Clash HTTP API в FFI не требуется.

## Параллельная работа в клиенте

Android-адаптер может подготовить записи графа и authenticated SOCKS-слушателей,
запустить библиотеку, дождаться готовности, затем запустить общий наблюдатель
в контексте VPN-сервиса. Probe-соединение идёт к loopback; подключение к
удалённому серверу выполняет BlazeCore с существующим `VpnService.protect`.
Остановка/отзыв VPN сначала отменяет наблюдатель и команды, затем ядро и TUN.

На iOS наблюдатель должен жить в `NEPacketTunnelProvider`, чтобы продолжать
работать после приостановки интерфейсного приложения. Swift/provider request
принимает ограниченный список записей полного графа с проверкой размера.
Расширение связывается с отдельной клиентской Rust staticlib `observer-bridge`:
подготовка добавляет фиксированные слушатели, общий Rust-наблюдатель выполняет
измерения и выбор, а тонкий C callback меняет selector той же core-сессии.
Swift управляет системным жизненным циклом, без отдельной реализации leastPing.
Сетевые сокеты BlazeCore
пользуются уже существующим callback защиты физического интерфейса. Внешний
процесс или постоянно работающее UI-приложение для этого не требуются.

Общий домен Blazer уже определяет members, порядок отчётов, integer-ms сравнение,
fallback и правила выбора. Платформенные адаптеры меняют транспорт команды,
не вводят отдельные варианты правил leastPing. Отсутствие capabilities у
старой библиотеки — ошибка поставки, которую устраняет новый проверенный bundle.

## Артефакты и доказательства

Android-упаковщик проверяет ревизию
`10512be664e2100bb4a0ad3bb95f6c70a184ee2d`, дерево
`ef9a083e67fe74e044e65735cff471c58e902f4b`, JNI-версию `0.3.7`, capability bit 1
и отдельный закреплённый SHA-256 каждого ABI. Проверенный x86_64 `.so`:
`064DA9243AD53DEB60C1AC464EDF2724118EA6AF5E957E6CBE7B9611E85E170A`.
Проверенный ARM64 `.so`:
`03470F1976B1286ECF7DFC4FB33BBF24272B29052965D8DEA5282FFFEE443298`.
Для обоих ABI проверены ELF-архитектура, selector exports и выравнивание LOAD
на 16 KiB; это проверка сборки, не замена запуску на физическом ARM64.
Manifest и реальные байты сверяются независимо. Исторический compiler build stamp
`0.3.7+gb90121c0406c.dirty` описывает состояние checkout во время сборки и не
заменяет JNI-версию либо закреплённую ревизию/дерево. Для обоих ABI принимается
только закреплённая новая библиотека; подмена или отсутствие ABI отклоняется.
Apple `.a`, C header, ревизию, SHA-256 и лицензии передаёт владелец ядра;
отключать проверки bundle нельзя.

На этой Windows-машине найдены SDK `C:\Development\Android\Sdk`, NDK r27c,
существующая Java и Rust targets Android ARM64/x64, iOS ARM64, macOS ARM64.
Для Android подготовлен изолированный AVD `Blazer_API_35`; тесты на нём отдельно
проверяют реальный TUN/JNI и версию артефакта. Mac/Xcode и физический iPhone
не представлены. Наличие toolchain или успешный Rust check не доказывают
работоспособность подписанного Apple Network Extension.

Приёмка ядра: live TUN с дополнительными SOCKS-слушателями, смена selector A→B
для нового TCP/UDP трафика при сохранении открытого, неверные refs/тип/handle,
старая команда после stop→start, немедленный отказ при занятом управлении,
отмена наблюдателя, отсутствие
открытых портов и фоновых задач после stop. Отдельно Android protect и Apple
packet-flow. Клиентская приёмка повторяет fastest→failure→fallback→recovery,
subset subjectSelector, GET с любым HTTP status, serial/concurrent интервалы,
отмену и работу при закрытом UI. Rust compile, APK build и реальный запуск
проверяются и фиксируются раздельно для Android и iOS.
