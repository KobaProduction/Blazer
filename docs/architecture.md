# Архитектурный контракт клиента

Продуктовые обязательства: [требования](product-requirements.md);
референс и границы паритета: [Happ](reference-behavior.md).
Справочник: [AI Agent Workflow / Clean Architecture / DDD](https://github.com/ArthurKoba/ai-agent-workflow/blob/main/skills/software-engineering/clean-architecture-ddd.md).
Требование в документации не означает реализованный VPN.

## Владение технической частью

Проект содержит один клиент. В `src/domain` и `src/application` находятся
общие правила, сценарии и контракт `ClientSession`. В `src/presentation`
расположены общие контроллеры, модели и адаптивный GUI. Платформенные точки
запуска и системные адаптеры находятся в `src/platform`.
Общие сценарии отвечают за подписки, профили и управление соединением.
Хранилище, ОС и BlazeCore подключаются через внешние адаптеры. Изменения самого
форка BlazeCore согласуются с владельцем ядра.

Цель совместимости — принимать текстовые списки ссылок, списки в Base64,
профили Xray/V2Ray и конфигурации sing-box, а поддерживаемые варианты
запускать через BlazeCore. Возможности объявляются по формату и протоколу после
проверки импорта и передачи данных. Домен определяет типы метаданных Happ.
Application применяет их правила при обновлении подписок, а UI использует
опубликованные состояния и действия.

Домен не имеет внешних зависимостей; application зависит только от домена.
GUI, OS API, SDK и конкретные реализации портов находятся во внешних слоях.
Та же граница действует для test/build dependencies. Dependency gate проверяет
разрешённый набор пакетов, наследование lint-правил, MIT собственных пакетов и отсутствие
GUI/window/webview библиотек в headless-графе. Он также проверяет пути пакетов
и отсутствие платформенных библиотек у общего `vpn-presentation`.

Изменяемое состояние принадлежит ядру клиента. GUI хранит screen enum и cached snapshot;
отрисовка не запрашивает engine status и не генерирует telemetry.
Ядро публикует статус при изменении состояния, включая завершение автоматического
обновления. GUI не добавляет постоянный repaint/poll timer. I/O-адаптеры требуют
отменяемого фонового исполнения; нельзя блокировать GUI-поток.

Для кнопки проверки отдельного сервера общий контроллер принимает
`Intent::ProbeProfile(profile_uuid)`. Действие доступно при
`snapshot.profile_probe_available && !snapshot.busy`. Настройки принадлежат
`Catalog.settings.probe`; команда `SetProbeSettings` проверяет и атомарно сохраняет
метод, GET/HEAD, URL, таймаут, прогрев, число измерений и стратегию результата.
GUI и CLI используют один контракт. Изменение настроек очищает прежние результаты.
Application находит сервер
по идентификатору в каталоге. Для TCP `ProfileProbePort` измеряет прямое
подключение к адресу сервера с выбранным таймаутом каждого замера. Для UDP и QUIC
движок выполняет HTTPS-запрос через локальный прокси. Временный экземпляр
BlazeCore проверяет трафик с выбранными параметрами и завершает работу. Для уже
активного профиля без пользовательской маршрутизации используется действующий
локальный прокси. Параллельное подключение с тем же ключом WireGuard блокируется.
В
`snapshot.profile_latencies[profile_uuid]` публикуется `Reachable { milliseconds }`,
`TimedOut`, `Unreachable` или ошибка запуска проверки. До первой проверки записи
и отметки в списке нет. Результат живёт
до удаления профиля или перезапуска сессии. При активном TUN в Windows проверка
текущего профиля в режиме «Авто» или «Через прокси» отправляет контрольный HTTP-запрос через маршруты уже работающего
туннеля, обходя настройки системного прокси. Второй экземпляр профиля WireGuard
или AmneziaWG не запускается. Для HTTP-проверки других профилей требуется отключение TUN,
чтобы не измерять вложенное подключение. Явный метод TCP измеряет соединение с
TCP-адресом сервера по текущим маршрутам ОС, в том числе при активном TUN.
ICMP реализован через Windows API и доступен после отключения TUN.
Адаптеры без возможности HTTP-проверки активного TUN и незавершённая
очистка соединения блокируют соответствующую проверку.

Метод «Авто» выбирает TCP для TCP-endpoint и HTTP через BlazeCore для UDP/QUIC.
Явный HTTP-метод использует выбранный профиль для всех поддерживаемых транспортов.
По умолчанию выбран HEAD по HTTPS с двумя измерениями. Для HTTPS прогрев обязателен
независимо от сохранённого флажка; для HTTP он настраивается. Прогрев исключается
из статистики. Идентичность TCP-соединения проверяется по локальному и удалённому
адресу сокета: запрос с новым соединением считается прогревом и не попадает в
результат. Повторные попытки ограничены числом настроенных измерений. Ресурс,
который постоянно закрывает соединение, возвращает `ProbeConnectionNotReusable`.
Все измерения одной
HTTP-проверки используют один runtime и один HTTP-клиент; тела ответов ограничены
256 КиБ и читаются до конца для повторного использования соединения. GET и HEAD
принимают успешный 2xx-ответ. Для каждого замера действует выбранный таймаут;
отмена прерывает всю последовательность. Итог — последнее, минимальное, среднее
или медианное значение среди 1–5 измерений. Параметры ограничены доменом,
сетевые библиотеки и нативный ICMP остаются в инфраструктуре.

Домен определяет ограничения каталога, действительность названий и правила
сохранения идентичности профиля после обновления. `ClientApplication` применяет
их в сценариях подписок, профилей и соединения. Он сохраняет кандидат через
`StateStorePort` перед заменой текущего состояния. Шифрование и размер файла
принадлежат `SealedCatalogStore`. DPAPI и Keystore реализуют его контракт
`CatalogProtection`.

## Текущий исполняемый контракт

Desktop, Android и headless используют `ClientHandle`. Один рабочий поток ядра исполняет
команды и публикует snapshot с результатом последнего обработанного запроса,
выбранным режимом и активным режимом. Переключение профиля при активном
соединении требует Disconnect. Disconnect доступен через резервный слот при
заполненной очереди и отменяет текущую загрузку или подготовку соединения.

В Windows `LocalProxy` запускает утверждённый BlazeCore и публикует один адрес IPv4 loopback
для SOCKS5 и HTTP CONNECT после сигнала готовности дочернего процесса и
локальной проверки SOCKS5. `SystemProxy` запускает тот же локальный слушатель,
затем применяет его HTTP-адрес к настройкам прокси текущего пользователя Windows.
Отдельный скрытый экземпляр `blazer --system-proxy-guard` владеет глобальным
именованным mutex пользователя, исходным снимком параметров и каналом к клиенту.
Он временно отключает PAC/WPAD и уведомляет WinINet об изменении. Состояние
`SystemProxy` публикуется только после подтверждения применения настроек.
При отключении настройки восстанавливаются до остановки локального слушателя.
EOF канала восстанавливает настройки и при принудительном завершении клиента.
Снимок восстановления сохраняется в HKCU с защитой DPAPI до изменения настроек.
После завершения всего дерева процессов следующий запуск Blazer возвращает
исходные настройки, если прокси ещё принадлежит прерванному подключению.
Изменённый пользователем адрес прокси не заменяется прежним снимком.
Проверки отдельных серверов используют `LocalProxy` и не меняют настройки ОС.
Ошибки применения и восстановления имеют отдельные типы; сбой восстановления
оставляет очистку незавершённой и не выдаёт успешное отключение.
В режиме Tun обычный процесс BlazeCore применяет выбранную исходящую цепочку
и правила маршрутизации. Служба BlazeCoreTun владеет Wintun, системными
маршрутами и DNS. Клиент проверяет, что служба запущена, и ждёт сигнала ядра
после активации маршрутов. Завершение рабочего процесса закрывает канал к
службе и освобождает ресурсы туннеля.
Android Activity отправляет типизированные намерения общему контроллеру через
JNI. Модуль `src/infrastructure/android` реализует адаптеры BlazeCore и
Keystore. JNI-контроллер подписывается на состояние и подключает эти адаптеры
к ядру клиента. Точки входа Android SDK объявлены в манифесте APK.
С доступной библиотекой BlazeCore Android предлагает режим `Tun`. После
системного согласия `VpnService` открывает TUN и владеет дескриптором до остановки
BlazeCore. Сокеты ядра исключаются из маршрута туннеля через `VpnService.protect`.
Служба отправляет `Connect(Tun)` и ждёт завершения по идентификатору команды.
При отказе до открытия туннеля служба завершается. Повторный запрос запуска
сохраняет действующий туннель.
Android подписывается на изменения сети типа VPN. Перед публикацией состояния
подключения адаптер подтверждает адрес и маршрут TUN, а также локальный ответ BlazeCore.
Application проверяет, что подтверждённый адаптером режим совпадает с запросом;
для TUN нет опубликованного SOCKS5 или HTTP CONNECT адреса. Каталог шифруется
через платформенный Keystore.

`SetLocalProxyPort` сохраняет порт общего слушателя SOCKS5 и HTTP CONNECT.
`0` выбирает свободный порт автоматически. Новый порт применяется при
следующем подключении LocalProxy. Снимок отдельно показывает сохранённый
порт и адрес текущего слушателя. Headless принимает `local-proxy-port <0-65535>`.

`blazer --cli status` читает локальное состояние и сообщает доступность режимов.
Консольный и графический режимы передают одинаковые типизированные `ClientCommand` в
`ClientHandle`; разбор аргументов и форматирование вывода остаются в headless.
`profiles` и `subscriptions` выдают UUID для команд. `profile select|test|remove`,
`subscription add|edit|rename|refresh|remove|fallback|clear-fallback|approve|reject`,
`language` и `mode` вызывают сценарии application. `settings` читает сохранённые
язык и режим, `diagnostics` выводит ограниченные события текущей сессии.
`import` читает конфигурацию из stdin до EOF. `subscription add`, `edit` и
`fallback` так же принимают URL через stdin. Список подписок показывает названия и
идентификаторы, а для подтверждения изменений провайдера показывает origin
и nonce. Переименование сохраняет текущий URL, профили и данные обновления.
В форме редактирования текущий URL по умолчанию замаскирован. Пользователь может
показать, скопировать или изменить его. Копирование также доступно в меню подписки.
Сохранение имени без смены URL вызывает `RenameSubscription`. Новый URL проверяется
и сохраняется вместе с обновлённым списком серверов. При активном подключении
через эту подписку сохранение нового URL требует отключения.
Для профиля каталог сохраняет ссылку импорта или JSON конкретного outbound.
`UpdateProfile` повторно разбирает конфигурацию одного сервера, проверяет её
в адаптере ядра и сохраняет с прежним UUID. Скрытые провайдером конфигурации
и профиль активного соединения защищены от изменения. Полное обновление
подписки может заменить локальную правку её профиля.
Команды подключения запускают выбранный профиль до Enter или EOF на stdin.
Режим `tun` требует подключённого системного адаптера. Данные Windows по умолчанию
хранятся в `%LOCALAPPDATA%\Blazer`. Путь к каталогу можно задать через
`BLAZER_DATA_DIR`, а путь к установленному отдельно ядру через
`BLAZER_BLAZECORE_PATH`. При запуске BlazeCore проверяются hash и версия.
В Windows клиент запускает рабочий процесс BlazeCore без окна и включает его в
отдельный Job Object до выполнения кода ядра. При штатной остановке адаптер
завершает этот объект и ждёт выхода процесса. При принудительном завершении
клиента Windows закрывает дескриптор объекта и останавливает рабочий BlazeCore.
Адаптер применяет ACL через Windows API к новому пустому рабочему каталогу.
Доступ получают текущий пользователь и SYSTEM, права родительского каталога
не наследуются. Только после этого адаптер подготавливает файлы запуска.
В Windows перед публикацией готовности подключения адаптер удаляет
временный `profile.yaml`, который BlazeCore уже загрузил. При ошибке удаления
адаптер отменяет запуск и останавливает ядро.

## Профили маршрутизации и DNS

Каталог хранит профили со стабильными UUID, ревизиями, упорядоченными
правилами и DNS. `SaveRoutingProfile`, `RemoveRoutingProfile`,
`SetRoutingAssignment` и `SetDnsPolicy` — общие команды application.
Встроенный вариант применяется при отсутствии общего профиля и разрешает
весь трафик через профиль прокси. Включённое назначение подписки имеет
приоритет над общим профилем. Выключенное или пустое назначение наследует
общий вариант. Удаление требует снять ссылки и завершить сессию, если она
использует выбранный профиль. Удаление подписки очищает её назначение.

Снимок публикует каталог, сохранённый выбор для выбранного сервера, активную
ревизию и ожидающую политику для фактически подключённого сервера. Если
сохранённое изменение затронуло активную политику, desktop предлагает
«Применить сейчас» или «При следующем подключении». Закрытие окна откладывает
применение. Явная команда переподключения проверяет идентификатор текущего
соединения и ожидаемую ревизию, затем подключает тот же сервер в том же
режиме. При отложенном применении активная ревизия остаётся до следующего
подключения, когда ядро клиента снова читает каталог. Переименование сохраняется
без изменения ревизии правил. Возврат к правилам и DNS активного соединения
снимает необходимость переподключения.
Каталоги без данных маршрутизации получают прежнее поведение при загрузке.

Адаптер LocalProxy переводит точный домен, доменный суффикс или канонический
IPv4/IPv6 CIDR в правило BlazeCore. Порядок соответствует каталогу. Если
совпадений нет, используется профиль прокси. DNS применяется при разрешении
имён ядром в LocalProxy и в управляемом Windows TUN. Выбор включает текущий
автоматический режим, системный резолвер и явные TCP, DoT и DoH. Явный
резолвер использует указанный IP и порт, а DoT и DoH дополнительно проверяют
сертификат по имени сервера. Прокси-сервер может сам разрешать переданные ему
имена. В Windows DNS адаптера настраивает служба BlazeCoreTun. Android TUN
использует встроенную политику. Импорт правил поставщика и источники geo остаются
следующим этапом.

## Подписки и конфигурации

Снимок `subscription_usage` показывает предоставленные подпиской число
использованных байтов, лимит и срок действия по UUID. Парсер wire-метаданных
оставляет отсутствующие, неоднозначные и непредставимые счётчики пустыми.
Данные провайдера сохраняются в зашифрованном каталоге. UI получает числа
и не работает со строкой ответа. [Формат Happ](https://github.com/HappDev/happ_su/blob/main/dev-docs/app-management.md)

Запросы HTTPS-подписок по умолчанию передают `x-hwid` со случайным
идентификатором установки, который хранится в каталоге данных клиента.
Настройка «Передавать HWID» сохраняется между запусками. Её изменение
сбрасывает условные версии ответов подписок, чтобы следующий запрос получил
данные для нового режима. «Об устройстве» показывает тот же идентификатор,
который использует HTTP-адаптер. HWID не попадает в журнал и телеметрию.

HTTP(S) подписки и ручной импорт принимают текстовые списки ссылок и стандартный
или URL-safe Base64 с заполнением и без него. Можно подать Xray/V2Ray или
sing-box JSON напрямую или в Base64. Импорт поддерживает отдельный outbound,
список outbounds и массив совместимых обёрток с `outbounds`. Порядок доступных профилей
сохраняется. На весь документ действуют лимиты в 1 МиБ до и после
декодирования и 256 профилей. Валидированный
каталог сохраняется атомарной заменой зашифрованного файла. Windows использует
DPAPI текущего пользователя, Android хранит ключ в Keystore. Блокировка каталога
допускает одного владельца записи.

Application вызывает normalizer для перевода входного документа в типизированные
профили, затем проверяет их через порт выбранного движка перед изменением каталога.
Адаптер форматов не зависит от BlazeCore. Неподдержанный формат,
функция и недоступный engine имеют отдельные ошибки. Ручной импорт отклоняет
весь документ при ошибке. Разбираемая подписка сохраняет рабочие профили и описания
недоступных записей. Для недоступной записи каталог хранит отображаемые
название, протокол и причину. Если удалось проверить адрес и TCP-порт, каталог
сохраняет их для пинга вместе с отдельным идентификатором. Такие записи
доступны для просмотра и поиска. Подключение по ним остаётся недоступным.
Проверка всего ответа и замена каталога образуют одну операцию. При ошибке ответа
провайдера предыдущие записи сохраняются. Поддерживаемые профили включают SOCKS5, HTTP CONNECT, VLESS, VMess AEAD,
Trojan, Shadowsocks и Hysteria2. TCP, WebSocket с Host и path, TLS и совместимые варианты
VLESS Vision/REALITY преобразуются только там, где адаптер BlazeCore сохраняет их
семантику. Неподдерживаемая маршрутизация, DNS, цепочки, параметры безопасности
и транспорта дают явную причину недоступности. Поддерживаемый прямой upstream BlazeCore
также импортируется из JSON. QR-декодер передаёт распознанный текст тем же
сценариям импорта, что и буфер обмена. Закрытые форматы пока недоступны.

Windows принимает `.conf` WireGuard и AmneziaWG с одним peer и отдельные
клиентские профили BlazeCore в JSON и YAML. AmneziaWG передаётся BlazeCore как
профиль 3.1. Ключи, исходный текст и параметры протоколов хранятся в защищённом
каталоге. DNS-серверы из `.conf` задаются явными IP и опрашиваются по TCP
через выбранный туннель. Явная настройка DNS в профиле маршрутизации Blazer
имеет приоритет. Адреса вне `AllowedIPs` требуют явного прямого маршрута в
Blazer для split tunnel. TCP-проверка не запускается для UDP и QUIC.

Нативный импорт также принимает HTTP/1 и HTTP/2, SOCKS5, VLESS, VMess AEAD,
Trojan, Shadowsocks, Snell, Hysteria2, TUIC, AnyTLS, NaiveProxy и PortForward
с совместимыми клиентскими обёртками BlazeCore. Поддерживаются клиентские
записи и группы из одношаговых цепочек. Серверы, сложные цепочки, системные
настройки и локальные файлы ключей TLS требуют отдельного контракта. Возможности
Android зависят от версии встроенного ядра и проверяются отдельно.

SOCKS5-ссылки принимают обычный `user:password`, Base64 пары учётных данных
перед `@` и Base64 целого адреса с учётными данными. Закодированные пароли
сохраняют символы `%`, `@` и другие разделители как часть исходного значения.
[Форматы ссылок Happ](https://www.happ.su/main/dev-docs/examples-of-links-and-parameters).

Для TLS импорт сохраняет порядок ALPN из Xray JSON, sing-box JSON, URI и
VMess-ссылок v2rayN в Base64. Список хранится в зашифрованном каталоге и
передаётся BlazeCore как `alpn_protocols`. Для REALITY явный непустой
список ALPN отклоняется.
[Xray TLS](https://xtls.github.io/en/config/transports/tls.html),
[sing-box TLS](https://sing-box.sagernet.org/configuration/shared/tls/).

WebSocket Early Data сохраняется в каталоге. Импорт Xray JSON, URI и ссылок VMess
извлекает `ed` из пути WebSocket и передаёт в BlazeCore предел длины и заголовок
`Sec-WebSocket-Protocol`. Импорт sing-box JSON принимает `max_early_data` и
`early_data_header_name`. Пустое имя заголовка выбирает суффикс пути, если
в пути нет query-параметров. Предел зависит от доступной длины HTTP-строки
в закреплённом BlazeCore.
[Xray WebSocket](https://xtls.github.io/en/config/transports/websocket.html),
[sing-box WebSocket](https://sing-box.sagernet.org/configuration/shared/v2ray-transport/#websocket).

XHTTP и прежнее имя SplitHTTP распознаются в Xray JSON, URI и ссылках VMess
в Base64. Профиль хранит путь, HTTP authority и режим `auto`, `packet-up`,
`stream-up` или `stream-one`. Вместе с профилем сохраняются размещение и ключи
идентификатора сессии и номера пакета. Blazer принимает `sessionIDPlacement`,
`sessionIDKey`, `seqPlacement` и `seqKey`, включая поля в Xray `extra`, и передаёт
их BlazeCore как `session_id_placement`, `session_id_key`, `seq_placement` и
`seq_key`. Поддерживаются `path`, `query`, `header` и `cookie`. Номер пакета
передаётся в `packet-up`. Размещение по умолчанию — `path`.
Нестандартное размещение сохраняется общим валидатором и рендерером Windows и Android.
Диапазоны Xray `scMaxEachPostBytes` и `scMinPostsIntervalMs` задают размер
порции и интервал отправки. Клиент также передаёт поддержанные packet wire-параметры,
включая `uplinkHTTPMethod=GET`. Android использует закреплённое ядро из commit
`10512be` без прежнего запрета расширенных XHTTP-параметров. Регрессионные тесты
подтверждают валидацию и сохранение этих полей в TUN-конфигурации; они не заменяют
отдельную сетевую проверку XHTTP на каждой платформе.
Blazer сохраняет поддерживаемый профиль из `fp`, `tlsSettings.fingerprint`
или `realitySettings.fingerprint` и передаёт версию в конфигурацию BlazeCore.
`chrome` указывает на `hellochrome_155`, `firefox` — на `firefox-148`,
`safari` — на `hellosafari_26_3`. Явное имя версии сохраняется в профиле.
Подключение требует сборки ядра с соответствующим каталогом.
TCP-пинг измеряет
доступность адреса и порта. Для него не нужны TLS или обмен по XHTTP.
BlazeCore использует HTTP/1.1 без TLS, а при TLS
выбирает HTTP/2 по умолчанию или версию по единственному ALPN. `h3` формирует
QUIC-подключение с теми же SNI и проверкой сертификата. REALITY для VLESS
без Vision использует HTTP/2. Несколько ALPN, нестандартные заголовки,
отдельные параметры загрузки и прочие расширения XHTTP отклоняются при импорте.
[Xray XHTTP](https://xtls.github.io/en/config/transports/xhttp.html).

Hysteria2 импортируется из `hysteria2://`, `hy2://` и sing-box JSON, в том
числе из документов в Base64. Профиль хранит один порт, TLS с SNI и опциональный
Salamander. В URI `pinSHA256` закрепляет сертификат сервера по SHA-256, а
`insecure` отдельно управляет проверкой цепочки и имени. В sing-box
`network: "tcp"` отключает передачу пользовательских UDP-датаграмм.
Адаптер передаёт эти профили BlazeCore через QUIC с ALPN `h3`.
Диапазоны портов, Gecko, ECH, realm, SPKI pins из sing-box и фиксированные
лимиты пропускной способности отклоняются.
[Спецификация URI Hysteria2](https://v2.hysteria.network/docs/developers/URI-Scheme/),
[sing-box Hysteria2](https://sing-box.sagernet.org/configuration/outbound/hysteria2/).

VLESS `encryption` сохраняется из Xray JSON и URI, включая документы в Base64.
Адаптер BlazeCore проверяет форму настройки до записи каталога и передаёт исходную
строку ядру, сохраняя порядок ключей и блоков padding. Начальная проверка
криптографического материала и установление соединения принадлежат BlazeCore.
При включённом `encryption` Vision задаётся внутри протокола VLESS. При
`encryption=none` Vision требует TCP с TLS или REALITY. [Формат Xray VLESS](https://xtls.github.io/en/config/outbounds/vless.html),
[контракт BlazeCore](https://github.com/ArthurKoba/BlazeCore/blob/cce97a2c4c1c3bd0a07807f37a7caf3876c79110/docs/src/content/docs/protocols/vless-encryption.md).

Закреплённый BlazeCore принимает для VLESS и VMess UUIDv4 варианта RFC 4122.
Адаптер проверяет это при импорте до изменения каталога. Текстовые
идентификаторы Xray преобразуются в UUIDv5 по формату Xray. Их поддержка
требует версии BlazeCore, принимающей UUIDv5.
[Спецификация Xray UUID](https://github.com/XTLS/Xray-core/issues/158),
[валидатор закреплённого BlazeCore](https://github.com/ArthurKoba/BlazeCore/blob/cce97a2c4c1c3bd0a07807f37a7caf3876c79110/src/uuid_util.rs).

Для прямого ответа `200` от основного URL клиент может сохранить `ETag` в
зашифрованном каталоге вместе с проверенными профилями. Следующий GET к тому же
URL передаёт `If-None-Match`. При ответе `304` сценарий обновляет время последней
успешной проверки и сохраняет профили, выбор пользователя и политику Happ.
Метка не передаётся при редиректе или резервном запросе. Смена основного URL,
успешное обновление с резервного адреса или удаление профиля из подписки
сбрасывают метку. Ответы с `Cache-Control: no-store` или `Vary: *` обходятся
без сохранения метки. [Условные запросы HTTP](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-none-match).

Обновление может использовать один ранее сохранённый резервный URL при сбое
сети, таймауте или подходящем ответе HTTP. Последний рабочий набор профилей
остаётся в каталоге при неполучении валидной замены. Смена домена и новый
резервный адрес на другом origin из метаданных создают запрос на подтверждение.
UI получает origin и одноразовый nonce. Применение требует актуального nonce
и атомарного сохранения. Резервный ответ не может изменить адреса или политику
основной подписки. Полный успешный ответ основного адреса заменяет набор
метаданных. Ответ 304, сбой и успешный запрос к резервному адресу сохраняют
последние метаданные основного адреса. Настройки действуют в пределах своей
подписки и доступны без Happ Provider ID. `hide-settings` скрывает сведения
о её профилях. [Документация Happ](https://www.happ.su/main/dev-docs/app-management).

Запросы подписок по умолчанию отправляют `User-Agent: Blazer/<версия>`.
Значение можно изменить в настройках клиента.

Desktop и открытый Android-клиент ждут ближайшего срока в рабочем потоке ядра.
`profile-update-interval` задаёт положительное целое число часов от последней
успешной загрузки. При старте процесса просроченная подписка ставится в очередь;
`subscription-auto-update-open-enable` добавляет одно обновление этой подписки
на запуск. Директива `subscription-auto-update-enable` хранится как
метаданные и не меняет глобальные пользовательские настройки.

Application вычисляет сроки по состоянию подписок и полученным значениям
времени. Backend читает системные часы, ждёт ближайшего срока и запускает
общий сценарий проверки и атомарного обновления.
Ручные команды прерывают фоновый запрос. Прерванное автообновление остаётся
запланированным и может продолжиться после обработки ручных команд.
Подписка активного соединения ждёт отключения. При сбое автообновления
подписки с заданным интервалом клиент сохраняет рабочие профили и отметку сбоя
в зашифрованном каталоге. Отсрочка действует и после перезапуска клиента, в том
числе при обновлении на открытии. Ручное обновление доступно сразу, успешное
обновление снимает отсрочку. Ошибка видна в состоянии подписки до перезапуска.
Android передаёт ближайший срок системному `JobScheduler`.
Задача ОС использует отдельный `RefreshControl` для запуска и отмены пакетного
обновления. Она вызывает те же сценарии `ClientApplication` и обрабатывает
подписки, срок которых наступил. Правила обновления при открытии активируются
при старте Activity. Платформенное расписание и завершение системного задания
публикуются через `RefreshStatus`. `ClientSession` задаёт общий контракт для
Android, desktop и headless. Headless-команды выполняются в ручном режиме.

Небольшой protocol enum — словарь model contract, не feature matrix поддержки.
Реальная нормализованная схема расширяется под fixtures и версионированный
core contract, с отказом от неподдержанных полей без silent drop.

## Собственное модифицированное ядро

Граница текущей поддержки полных Xray-конфигураций и результаты сетевых
проверок собственных правил и групп ядра описаны в
[приёмке маршрутизации и балансировщиков](xray-balancer-acceptance.md).

Поддержанная полная Xray-конфигурация импортируется одним профилем
`ProxyProtocol::Graph`. Доменный `ProxyGraph` хранит именованные выходы,
группы Round Robin и leastPing, общую observatory, упорядоченные условия и цели
правил, маршрут по умолчанию и DNS-политику. Домен проверяет уникальность тегов и ссылки, ограничивает
число выходов, групп и правил до 256, суммарное число узлов условий до 256
и глубину условий до восьми. Участники группы ссылаются на выходы; вложенные
графы профилей и пустые группы отклоняются. Контракт находится в
`src/domain/client/graph.rs`.

Адаптер импорта Xray сохраняет полный исходный JSON для редактирования
в `source` защищённого профиля. Каталог сохраняет и восстанавливает весь граф
через отдельный DTO и штатную защиту хранилища; на Windows это DPAPI.
Неподдержанные стратегии и поля дают явный отказ. Текущий исполняемый набор —
`AsIs`, `roundRobin`, `leastPing` с observatory, точные домены, доменные суффиксы, CIDR и условия TCP/UDP,
а также выходы direct/block. Граница входных слушателей, DNS и остальных
стратегий определена в приёмке. Преобразование и хранение принадлежат
`src/infrastructure/client_normalize/xray_graph.rs`,
`src/infrastructure/client_engine/graph.rs` и
`src/infrastructure/client_store/graph.rs`.

Application выбирает, обновляет и подключает групповой профиль через общие
порты ядра клиента. Инфраструктура преобразует полный граф в именованные
цепочки, группы и правила BlazeCore. Пользовательские правила сохраняют
порядок: `Proxy` передаёт совпавший трафик графу провайдера, `Direct` и `Block`
применяют своё действие. После пользовательских правил применяется граф
провайдера с его маршрутом по умолчанию. Метод проверки «Авто» использует
для группового профиля движок и весь граф; адрес представительного сервера
служит отображению и не подменяет такую проверку прямым TCP-соединением.
GUI и CLI вызывают те же сценарии; логика выбора выходов остаётся вне UI.

Для leastPing общий наблюдатель инфраструктуры проверяет раскрытый
`subjectSelector` через закреплённые выходы того же процесса BlazeCore.
Проверка выполняет GET без перехода по перенаправлениям, принимает любой
HTTP-статус и измеряет время до получения заголовков. Таймаут — пять секунд;
URL и расписание принадлежат observatory, не настройкам ручного пинга.
Последовательный режим проверяет теги по алфавиту с паузой после каждого;
параллельный запускает раунд вместе и делает паузу после завершения раунда.
Один общий набор результатов используется всеми группами leastPing.

Чистая доменная политика выбирает живого участника с минимальным временем,
округлённым вниз до миллисекунд. При равенстве сохраняется порядок первого
поступления отчётов; обновление отчёта не меняет его позицию. Отказ исключает
прежний успешный результат, ещё не проверенный участник не считается живым.
Если живых участников нет, выбирается `fallbackTag`, затем глобальный выход
графа по умолчанию. Это отдельный контракт клиента поверх нативного selector
BlazeCore: изменение выбора влияет на новые соединения, а открытые потоки
сохраняют прежний выход. Наблюдение отменяется при остановке сессии;
управляющий API и локальные входы проверки защищены случайным секретом сессии.

Приёмка поставляемого Windows-клиента подтвердила эту цепочку в LocalProxy
с реальными локальными выходами, переключением leastPing, резервным выходом
и сохранением открытого потока. Android подключает тот же наблюдатель к
единственной сессии TUN через JNI. Команда выбора захватывает handle сессии
при создании наблюдателя и передаёт его неизменно; старый callback не получает
handle следующей сессии. Отсутствие selector capability в загруженной библиотеке
даёт явный отказ. Требуемый контракт и статус поставки артефактов определены в
[запросе API ядра](core-selector-ffi-request.md).

В Apple Packet Tunnel тонкая библиотека `observer-bridge` связывает расширение
Swift с общим Rust-наблюдателем без зависимости от GUI. Расписание, HTTP-проверки
и выбор не дублируются в Swift. Наблюдатель запускается после готовности ядра
и останавливается перед ним; callbacks непосредственно вызывают потокобезопасный
API selector с захваченным handle. Пакет включает статическую библиотеку клиента
и сгенерированный `safer-ffi` заголовок; собственный Rust-код сохраняет запрет
unsafe. Параметры полного графа и фиксированные входы помещаются в ограниченный
запрос до 64 КиБ, переполнение отклоняется без усечения. Apple Rust-код прошёл
cross-check для iOS; сборка Swift, итоговая линковка расширения и сетевой запуск
требуют Mac с Xcode и отдельно не подтверждены.

22 ноября 2026 года Android 15 x86_64 прошёл реальную сетевую приёмку TUN/JNI
с доверенной библиотекой BlazeCore из исходного дерева commit `10512be`:
выбор A → B → fallback C → A, сохранение открытого потока, остановка и отказ
устаревшего handle после нового старта. Полные реквизиты артефакта и границы
проверки находятся в [приёмке балансировщиков](xray-balancer-acceptance.md).
Сетевой запуск того же графа через Windows TUN отдельно не подтверждён;
Windows LocalProxy использует прежний закреплённый бинарный артефакт.

Источник ядра — [ArthurKoba/BlazeCore](https://github.com/ArthurKoba/BlazeCore),
его [архитектура](https://github.com/ArthurKoba/BlazeCore/blob/master/docs/architecture.md)
владеет engine runtime/Device/Session и core/app contract. Не копировать его
schema в клиент. Windows-адаптер проверяет известный артефакт BlazeCore,
преобразует поддерживаемый профиль в приватную конфигурацию и управляет
дочерним процессом. В режиме `LocalProxy` он публикует loopback-адрес.
В режиме Tun Blazer передаёт BlazeCore профиль управляемого туннеля и
ожидает готовности процесса. Установка службы и поставка драйвера
определены в платформенном контракте BlazeCore.

Application обращается к движку через `ClientEnginePort`. Проверка системного
туннеля требует передачи данных через интерфейс ОС и проверки его очистки.
Статус этих проверок для каждой системы хранится в [платформенном контракте](platforms.md).

## Нативный GUI и ресурсы

Общий интерфейс Blazer построен на [egui](https://docs.rs/egui/0.37.0/egui/).
`client-ui` выбирает компоновку по текущей ширине окна. Точки входа под
`src/platform` отвечают за системные возможности и рендерер. Windows
подключает eframe с Glow и передаёт экранам штатный диалог открытия файла,
захват экрана и сведения об ОС. Домен, сценарии и ядро клиента остаются независимыми
от рендерера и компоновки.

## Переезд на общий egui

1. Windows служит эталоном трёх компоновок. При переходе через 600 и 900
   логических пунктов сохраняются состояние экрана, поиск и черновики форм.
2. Android открывает общий `BlazerView` через JNI и `GLSurfaceView` при обычном
   запуске. Сессия остаётся на уровне процесса и обслуживает VPN и фоновые
   обновления после закрытия окна. Activity владеет поверхностью, системным
   согласием на VPN, камерой, выбором файла и переходом к каналу обновлений.
3. Linux использует тот же UI через eframe/Glow. Secret Service хранит ключ
   каталога. Платформа передаёт защиту каталога и процесс BlazeCore в ядро клиента.
   В режиме TUN адаптер проверяет доступ к системным возможностям и передаёт
   профиль BlazeCore. Маршруты и правила освобождает сам BlazeCore по SIGTERM.
4. macOS и iOS подключают `BlazerView` и `client-core` через общий Metal-хост.
   Ключ каталога хранит Keychain. macOS запускает закреплённый процесс
   BlazeCore для локального прокси. Сборки `ios-device` и `macos-tunnel` передают
   выбранный профиль в общий Packet Tunnel Provider через параметры запуска.
   Системный профиль хранит идентификатор расширения и адрес сервера.
   Провайдер передаёт IP-пакеты BlazeCore через его C ABI. iOS загружает его
   как расширение приложения, macOS активирует как system extension.

Уровни приёмки по каждой ОС перечислены в [платформенном контракте](platforms.md).
`client-cli` вызывает `client-core` напрямую. В будущей сборке для OpenWrt
долгоживущая сессия будет принадлежать демону. Веб-интерфейс и CLI смогут
отправлять команды и читать состояние через локальный интерфейс управления
демона. Протокол управления, target, ABI и libc OpenWrt ещё предстоит выбрать.
Ресурсы измеряются по [performance contract](performance.md); Rust сам по себе
не доказывает энергоэффективность.

## Версионирование и выпуски

Источник версии выпуска — стабильный Git-тег `vX.Y` на `HEAD`. Архив
для GitHub собирается из чистого checkout с одним таким тегом. Скрипт передаёт
версию в Rust при сборке. Она используется в `VERSIONINFO`, `--version`,
GUI, User-Agent по умолчанию и OpenTelemetry. Для обычной локальной сборки
источник версии — `workspace.package.version` в `Cargo.toml`.
Identity-bearing Setup требует чистого checkout: stable — только `-ReleaseArchive`
на теге, обычный `-Installer` — preview. `-DevelopmentInstaller` создаёт отдельный
неустанавливаемый compile-check executable из текущих исходников; он не публикуется
и не представляет dirty-байты как immutable release.
Android берёт `versionName` из тега для прямого выпуска или debug APK с
`-TaggedVersion`. Значение `versionCode` по умолчанию равно
`1 + X × 1 000 000 + Y × 1 000` при `X ≤ 2099` и `Y ≤ 999`.
Параметр `-VersionCode` назначает отдельный номер сборки. Для одного Android
application ID этот номер должен расти при каждой публикации, включая повторную
сборку того же `versionName`. iOS записывает `X.Y.0` в `CFBundleShortVersionString`
и хранит отдельный `CFBundleVersion`. [Подготовка выпуска для Apple](https://developer.apple.com/documentation/Xcode/preparing-your-app-for-distribution)

Следуя разделению в RedmiBook Manager, `vpn-application` владеет политикой
версии и build identity, Windows-адаптер проверяет GitHub и установщик,
а `client-ui` показывает состояния. Маркетинговая версия остаётся `X.Y`,
идентичность сборки содержит полный коммит и положительный bounded sequence
из `git rev-list --first-parent --count HEAD`. Стабильный канал читает
`/releases/latest` и не принимает preview. Preview сначала проверяет стабильный
выпуск для перехода с тем же или более новым `X.Y`, затем `/releases/tags/preview`.
Новое preview с тем же `X.Y` требует другого коммита и большего sequence;
повтор текущего коммита не предлагается. HTTPS override `BLAZER_RELEASE_FEED_URL`
сохраняет тот же строгий контракт метаданных.

Основной артефакт — `Blazer-X.Y-windows-x86_64-setup.exe`, для preview —
`Blazer-preview-COMMIT12-SEQUENCE-windows-x86_64-setup.exe`.
Парный `-update.json` содержит schema, version, channel, sequence, commit и
setup `{name,size,sha256}`. Клиент проверяет bounded JSON, его GitHub SHA-256,
согласованность канала, версии и имени, точный URL этого репозитория, digest и
размер Setup в JSON и GitHub API, затем фактические скачанные байты.
Authenticode не объявляется проверенным: доверие этой поставки основано на
HTTPS GitHub и закреплённых метаданных, а не на отсутствующем сертификате подписи.

Workflow `releases.yml` обновляет существующий prerelease `preview` после пуша
в `main`. Он загружает новый Setup, парный JSON и внутренний ZIP ядра,
проверяет их SHA-256 на GitHub, переносит тег `preview` на собранный коммит
и удаляет прежние артефакты этого канала. Номер
прогона GitHub Actions и коммит указываются в описании сборки. Стабильные теги
`vX.Y` и их выпуски публикуются отдельно по явному пушу тега. Windows-клиент
на стабильном канале читает только `/latest`. Установленный prerelease может
перейти на стабильный выпуск с тем же `X.Y`.

Первый `preview` содержит локально упакованный закреплённый BlazeCore.
Следующие запуски берут его и лицензии из опубликованного ZIP. При смене
закреплённого ядра CI может получить архив с новыми файлами через переменную
репозитория `BLAZER_WINDOWS_ENGINE_ARCHIVE_URL`. Упаковщик всегда сверяет
SHA-256 ядра с утверждённым значением в исходниках.

ZIP остаётся только внутренним источником закреплённого ядра для release-сборки,
не запасным форматом updater. Обновление приложения выполняет тот же NSIS Setup,
который отвечает за клиент, ядро, Wintun и службу. Встроенная установка доступна
только из управляемого `Program Files\Blazer` с согласованными protected HKLM и
`blazer-installation.json`; portable-каталог получает ссылку на мастер установки.
Проверенный Setup удерживается read-lock до завершения мастера и запускается
обычным процессом с `/UPDATE`. Он сам запрашивает UAC после подтверждения;
updater не закрывает окно при запуске или отмене. Установщик закрывает только
подтверждённые процессы управляемого продукта перед транзакцией службы/файлов.
Ошибки и код завершения показываются пользователю. Каталог пользовательских
данных не входит в пакет. Подробнее: [Windows installation](windows-installation.md).
Правила распространения для Android и iOS описаны
в [платформенном контракте](platforms.md#каналы-мобильных-обновлений).

## OpenTelemetry и диагностика

Ядро клиента использует OpenTelemetry 0.33.1 для трейсов, метрик и
структурированных событий. Текущая сборка не задаёт адрес и токен.
В «Настройки → Телеметрия» можно отключить отправку или настроить её вручную.
Ручное сохранение отправляет в `/v1/logs` пустой OTLP/HTTP protobuf-запрос
с таймаутом 1,5 секунды. Только после подтверждения коллектора новый URL и
необязательный Bearer-токен сохраняются в защищённом каталоге и используются
для новых событий. При ошибке продолжают действовать предыдущие настройки.
Экран получает признак сохранённого токена.
Пустое поле сохраняет токен для прежнего URL. При смене URL введите токен
нового коллектора или оставьте поле пустым для запроса без авторизации.

Для развёртывания укажите базовый URL в `OTEL_ENDPOINT` и при
необходимости сырой токен в `OTEL_BEARER_TOKEN`. Blazer сам формирует
`Authorization: Bearer …`. Приоритет имеет `OTEL_ENDPOINT` процесса.
Затем учитываются стандартные параметры SDK `OTEL_EXPORTER_OTLP_*` со своими
заголовками. Последний вариант — значение `OTEL_ENDPOINT` при компиляции,
если оно задано. Для него токен можно передать процессу при запуске.
Токен в артефакт сборки не включается. Ручной режим задаёт URL и Bearer
из настроек Blazer. Явное отключение в приложении имеет приоритет над
параметрами среды и сборки. [Контракт Services Deployment](https://github.com/ArthurKoba/ai-agent-workflow/blob/main/skills/services-deployment/telemetry-variables.md)
Общий адрес `http://127.0.0.1:4318` направит OTLP/HTTP protobuf в
`/v1/traces`, `/v1/metrics` и `/v1/logs`. Для удалённого коллектора с
авторизацией задайте HTTPS-адрес. `OTEL_SDK_DISABLED=true` отключает
экспорт при следующем запуске независимо от выбранного режима.
Формат путей соответствует [спецификации OTLP](https://opentelemetry.io/docs/specs/otel/protocol/exporter/).

На стороне коллектора видны имя сервиса `blazer`, версия приложения,
категория операции, её результат, время и служебные идентификаторы SDK.
Метрики `blazer.client.events`, `blazer.client.operation.duration` и
`blazer.client.diagnostic.events.dropped` описывают события клиента, длительность
операций в секундах и вытеснение записей из локального буфера. URL и токены
подписок, имена и адреса профилей, HWID, детали HTTP-ответа и сетевой трафик
в экспорт не входят. Полные снимки состояния остаются внутри клиента.

SDK отправляет ограниченные пакеты на фоновых потоках. Сбой коллектора
не меняет операции VPN. При завершении ядро клиента сначала освобождает ресурсы
подключения, затем завершает экспорт. Диагностика в окне получает до
128 последних событий из локального буфера. Headless показывает
`telemetry_export=configured` при настроенном экспорте и
`telemetry_export=not_configured` при отключённом. Доступность коллектора
проверяется по приёму сигналов.
