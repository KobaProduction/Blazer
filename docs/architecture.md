# Архитектурный контракт клиента

Продуктовые обязательства: [требования](product-requirements.md);
референс и границы паритета: [Happ](reference-behavior.md).
Справочник: [AI Agent Workflow / Clean Architecture / DDD](https://github.com/ArthurKoba/ai-agent-workflow/blob/main/skills/software-engineering/clean-architecture-ddd.md).
Требование в документации не означает реализованный VPN.

## Владение технической частью

Проект содержит один клиент. В `src/domain` и `src/application` находятся
общие правила, сценарии и контракт `ClientSession`. В `src/presentation`
расположены общие контроллеры и модели, а также платформенные способы запуска.
Общие сценарии отвечают за подписки, профили и управление соединением.
Хранилище, ОС и Shoes подключаются через внешние адаптеры. Изменения самого
форка Shoes согласуются с владельцем ядра.

Цель совместимости — принимать текстовые списки ссылок, списки в Base64,
профили Xray/V2Ray и конфигурации sing-box, а поддерживаемые варианты
запускать через Shoes. Возможности объявляются по формату и протоколу после
проверки импорта и передачи данных. Домен определяет типы метаданных Happ.
Application применяет их правила при обновлении подписок, а UI использует
опубликованные состояния и действия.

## Границы пакетов

| Пакет | Ответственность | Разрешённые внутренние зависимости |
| --- | --- | --- |
| `vpn-domain` | Предметные значения и инварианты | Нет |
| `vpn-application` | Сценарии, правила автообновления, import guard, engine/normalizer ports, типизированные ошибки | `vpn-domain` |
| `vpn-infrastructure` | Реализации внешних портов | `vpn-application`, `vpn-domain` |
| `vpn-backend` | Общая composition root, worker, часы и ожидание обновлений, OTel/диагностика | `vpn-infrastructure`, `vpn-application` |
| `vpn-presentation` | Общие контроллер, модели и локализация | `vpn-application` |
| `vpn-image-import` | Декодирование QR из изображений и кадров камеры | `vpn-presentation` |
| `vpn-client` | Desktop GUI и сборка графа зависимостей Windows | `vpn-backend`, `vpn-presentation`, `vpn-image-import` |
| `vpn-android` | Android Activity, JNI-контроллер и сборка графа зависимостей Android | `vpn-backend`, `vpn-presentation`, `vpn-image-import`, адаптеры `vpn-infrastructure` |
| `vpn-headless` | Консольная доставка без окна | `vpn-backend` |

Домен не имеет внешних зависимостей; application зависит только от домена.
GUI, OS API, SDK и конкретные реализации портов находятся во внешних слоях.
Та же граница действует для test/build dependencies. Dependency gate проверяет
разрешённый набор пакетов, наследование lint-правил, MIT собственных пакетов и отсутствие
GUI/window/webview библиотек в headless-графе. Он также проверяет пути пакетов
и отсутствие платформенных библиотек у общего `vpn-presentation`.

Mutable состояние принадлежит backend. GUI хранит screen enum и cached snapshot;
отрисовка не запрашивает engine status и не генерирует telemetry.
Статус публикуется при изменении backend, включая завершение автоматического
обновления. GUI не добавляет постоянный repaint/poll timer. I/O-адаптеры требуют
отменяемого фонового исполнения; нельзя блокировать GUI-поток.

Для кнопки проверки отдельного сервера общий контроллер принимает
`Intent::ProbeProfile(profile_uuid)`. Действие доступно при
`snapshot.tcp_probe_available && !snapshot.busy`. Application находит сервер
по идентификатору в каталоге и вызывает `ProfileProbePort`. Групповая проверка
использует тот же порт. Infrastructure измеряет
время TCP-подключения к endpoint через текущий системный маршрут. Общий
таймаут вместе с DNS составляет 3 секунды. В
`snapshot.profile_latencies[profile_uuid]` публикуется `Reachable { milliseconds }`,
`TimedOut` или `Unreachable`. До первой проверки записи нет. Результат живёт
до удаления профиля или перезапуска сессии. При активном TUN или незавершённой
очистке соединения команда недоступна. HTTP-проверки через прокси и ICMP
требуют отдельных адаптеров и сценариев.

Домен определяет ограничения каталога, действительность названий и правила
сохранения идентичности профиля после обновления. `ClientApplication` применяет
их в сценариях подписок, профилей и соединения. Он сохраняет кандидат через
`StateStorePort` перед заменой текущего состояния. Шифрование и размер файла
принадлежат `SealedCatalogStore`. DPAPI и Keystore реализуют его контракт
`CatalogProtection`.

## Текущий исполняемый контракт

Desktop, Android и headless используют `ClientHandle`. Один backend worker исполняет
команды и публикует snapshot с результатом последнего обработанного запроса,
выбранным режимом и активным режимом. Переключение профиля при активном
соединении требует Disconnect. Disconnect доступен через резервный слот при
заполненной очереди и отменяет текущую загрузку или подготовку соединения.

В Windows `LocalProxy` запускает утверждённый Shoes и публикует один адрес IPv4 loopback
для SOCKS5 и HTTP CONNECT после сигнала готовности дочернего процесса и
локальной проверки SOCKS5. `SystemProxy` остаётся недоступным. Windows-адаптер
`Tun` использует Wintun и передаёт пакеты в тот же Shoes через loopback SOCKS5.
Маршрут к выбранному адресу сервера закрепляется до включения маршрутов TUN.
Адрес фиксируется на время сессии, а исходные TLS SNI и WebSocket Host сохраняются.
Перед включением маршрутов адаптер ждёт готовности адресов IPv4 и IPv6.
Затем он проверяет наличие всех требуемых маршрутов, в том числе уже существовавших.
При изменении таблицы адаптер перепроверяет маршруты. При потере обязательного
маршрута адаптер останавливает туннель, а backend публикует ошибку сессии.
Адаптер учитывает добавленные им маршруты и снимает их при отключении.
Android Activity отправляет типизированные намерения общему контроллеру через
JNI. Модуль `src/infrastructure/android` реализует адаптеры Shoes и
Keystore. JNI-контроллер подписывается на состояние и подключает эти адаптеры
к общему backend. Точки входа Android SDK объявлены в манифесте APK.
С доступной библиотекой Shoes Android предлагает режим `Tun`. После
системного согласия `VpnService` открывает TUN и владеет дескриптором до остановки
Shoes. Сокеты ядра исключаются из маршрута туннеля через `VpnService.protect`.
Служба отправляет `Connect(Tun)` и ждёт завершения по идентификатору команды.
При отказе до открытия туннеля служба завершается. Повторный запрос запуска
сохраняет действующий туннель.
Android подписывается на изменения сети типа VPN. Перед публикацией состояния
подключения адаптер подтверждает адрес и маршрут TUN, а также локальный ответ Shoes.
Application проверяет, что подтверждённый адаптером режим совпадает с запросом;
для TUN нет опубликованного SOCKS5 или HTTP CONNECT адреса. Каталог шифруется
через платформенный Keystore.

`SetLocalProxyPort` сохраняет порт общего слушателя SOCKS5 и HTTP CONNECT.
`0` выбирает свободный порт автоматически. Новый порт применяется при
следующем подключении LocalProxy. Снимок отдельно показывает сохранённый
порт и адрес текущего слушателя. Headless принимает `local-proxy-port <0-65535>`.

`vpn-headless status` читает локальное состояние и сообщает доступность режимов.
`vpn-headless` и GUI передают одинаковые типизированные `ClientCommand` в
`ClientHandle`; разбор аргументов и форматирование вывода остаются в headless.
`profiles` и `subscriptions` выдают UUID для команд. `profile select|test|remove`,
`subscription add|edit|rename|refresh|remove|fallback|clear-fallback|approve|reject`,
`language` и `mode` вызывают сценарии application. `settings` читает сохранённые
язык и режим, `diagnostics` выводит ограниченные события текущей сессии.
`import` читает конфигурацию из stdin до EOF. `subscription add`, `edit` и
`fallback` так же принимают URL через stdin. Список подписок показывает названия и
идентификаторы, а для подтверждения изменений провайдера показывает origin
и nonce. Переименование сохраняет текущий URL, профили и данные обновления.
В общей форме редактирования пустой URL переводится в `RenameSubscription`.
Команды подключения запускают выбранный профиль до Enter или EOF на stdin.
Режим `tun` требует подключённого системного адаптера. Для отдельного каталога
или установленного отдельно Shoes можно задать `VPN_CLIENT_DATA_DIR` и
`VPN_CLIENT_SHOES_PATH`. При запуске Shoes проверяются hash и версия.
В Windows клиент запускает рабочий процесс Shoes без окна и включает его в
отдельный Job Object до выполнения кода ядра. При штатной остановке адаптер
завершает этот объект и ждёт выхода процесса. При принудительном завершении
клиента Windows закрывает дескриптор объекта и останавливает рабочий Shoes.
Адаптер применяет ACL через Windows API к новому пустому рабочему каталогу.
Доступ получают текущий пользователь и SYSTEM, права родительского каталога
не наследуются. Только после этого адаптер подготавливает файлы запуска.
В Windows перед публикацией готовности локального прокси адаптер удаляет
временный `profile.yaml`, который Shoes уже загрузил. При ошибке удаления
адаптер отменяет запуск и останавливает ядро.

## Профили маршрутизации и DNS

Каталог хранит профили со стабильными UUID, ревизиями, упорядоченными
правилами и DNS. `SaveRoutingProfile`, `RemoveRoutingProfile`,
`SetRoutingAssignment` и `SetDnsPolicy` — общие команды application.
Встроенный вариант применяется при отсутствии общего профиля и разрешает
весь трафик через профиль прокси. Включённое назначение подписки имеет
приоритет над общим профилем. Выключенное или пустое назначение наследует
общий вариант. Удаление требует снять ссылки и завершить сессию, если она
использует выбранный профиль. Удаление подписки очищает её назначение.

Снимок публикует каталог, сохранённый выбор для выбранного сервера, активную
ревизию и ожидающую политику для фактически подключённого сервера. Если
сохранённое изменение затронуло активную политику, desktop предлагает
«Применить сейчас» или «При следующем подключении». Закрытие окна откладывает
применение. Явная команда переподключения проверяет идентификатор текущего
соединения и ожидаемую ревизию, затем подключает тот же сервер в том же
режиме. При отложенном применении активная ревизия остаётся до следующего
подключения, когда backend снова читает каталог. Переименование сохраняется
без изменения ревизии правил. Возврат к правилам и DNS активного соединения
снимает необходимость переподключения.
Каталоги без данных маршрутизации получают прежнее поведение при загрузке.

Адаптер LocalProxy переводит точный домен, доменный суффикс или канонический
IPv4/IPv6 CIDR в правило Shoes. Порядок соответствует каталогу. Если
совпадений нет, используется профиль прокси. DNS применяется внутри
слушателя LocalProxy при разрешении имён ядром. Выбор включает текущий
автоматический режим, системный резолвер и явные TCP, DoT и DoH. Явный
резолвер использует указанный IP и порт, а DoT и DoH дополнительно проверяют
сертификат по имени сервера. Прокси-сервер может сам разрешать переданные ему
имена. Настройки DNS ОС остаются отдельной ответственностью адаптера TUN.
Системные туннели принимают встроенную политику до отдельной проверки
персональных правил. Импорт правил поставщика и источники geo остаются
следующим этапом.

## Подписки и конфигурации

Снимок `subscription_usage` показывает предоставленные подпиской число
использованных байтов, лимит и срок действия по UUID. Парсер wire-метаданных
оставляет отсутствующие, неоднозначные и непредставимые счётчики пустыми.
Данные провайдера сохраняются в зашифрованном каталоге. UI получает числа
и не работает со строкой ответа. [Формат Happ](https://github.com/HappDev/happ_su/blob/main/dev-docs/app-management.md)

Запросы HTTPS-подписок по умолчанию передают `x-hwid` со случайным
идентификатором установки, который хранится в каталоге данных клиента.
Настройка «Передавать HWID» сохраняется между запусками. Её изменение
сбрасывает условные версии ответов подписок, чтобы следующий запрос получил
данные для нового режима. «Об устройстве» показывает тот же идентификатор,
который использует HTTP-адаптер. HWID не попадает в журнал и телеметрию.

HTTP(S) подписки и ручной импорт принимают текстовые списки ссылок и стандартный
или URL-safe Base64 с заполнением и без него. Можно подать Xray/V2Ray или
sing-box JSON напрямую или в Base64. Импорт поддерживает отдельный outbound,
список outbounds и массив совместимых обёрток с `outbounds`. Порядок доступных профилей
сохраняется. На весь документ действуют лимиты в 1 МиБ до и после
декодирования и 256 профилей. Валидированный
каталог сохраняется атомарной заменой зашифрованного файла. Windows использует
DPAPI текущего пользователя, Android хранит ключ в Keystore. Блокировка каталога
допускает одного владельца записи.

Application вызывает normalizer для перевода входного документа в типизированные
профили, затем проверяет их через порт выбранного движка перед изменением каталога.
Адаптер форматов не зависит от Shoes. Неподдержанный формат,
функция и недоступный engine имеют отдельные ошибки. Ручной импорт отклоняет
весь документ при ошибке. Разбираемая подписка сохраняет рабочие профили и описания
недоступных записей. Для недоступной записи каталог хранит отображаемые
название, протокол и причину. Если удалось проверить адрес и TCP-порт, каталог
сохраняет их для пинга вместе с отдельным идентификатором. Такие записи
доступны для просмотра и поиска. Подключение по ним остаётся недоступным.
Проверка всего ответа и замена каталога образуют одну операцию. При ошибке ответа
провайдера предыдущие записи сохраняются. Поддерживаемые профили включают SOCKS5, HTTP CONNECT, VLESS, VMess AEAD,
Trojan, Shadowsocks и Hysteria2. TCP, WebSocket с Host и path, TLS и совместимые варианты
VLESS Vision/REALITY преобразуются только там, где адаптер Shoes сохраняет их
семантику. Неподдерживаемая маршрутизация, DNS, цепочки, параметры безопасности
и транспорта дают явную причину недоступности. Поддерживаемый прямой upstream Shoes
также импортируется из JSON. QR-декодер передаёт распознанный текст тем же
сценариям импорта, что и буфер обмена. Закрытые форматы пока недоступны.

SOCKS5-ссылки принимают обычный `user:password`, Base64 пары учётных данных
перед `@` и Base64 целого адреса с учётными данными. Закодированные пароли
сохраняют символы `%`, `@` и другие разделители как часть исходного значения.
[Форматы ссылок Happ](https://www.happ.su/main/dev-docs/examples-of-links-and-parameters).

Для TLS импорт сохраняет порядок ALPN из Xray JSON, sing-box JSON, URI и
VMess-ссылок v2rayN в Base64. Список хранится в зашифрованном каталоге и
передаётся Shoes как `alpn_protocols`. Каталоги прежних версий читаются с
пустым списком. Для REALITY явный непустой список ALPN отклоняется.
[Xray TLS](https://xtls.github.io/en/config/transports/tls.html),
[sing-box TLS](https://sing-box.sagernet.org/configuration/shared/tls/).

WebSocket Early Data сохраняется в каталоге. Импорт Xray JSON, URI и ссылок VMess
извлекает `ed` из пути WebSocket и передаёт в Shoes предел длины и заголовок
`Sec-WebSocket-Protocol`. Импорт sing-box JSON принимает `max_early_data` и
`early_data_header_name`. Пустое имя заголовка выбирает суффикс пути, если
в пути нет query-параметров. Прежние записи каталога открываются с выключенным
Early Data. Предел зависит от доступной длины HTTP-строки в закреплённом Shoes.
[Xray WebSocket](https://xtls.github.io/en/config/transports/websocket.html),
[sing-box WebSocket](https://sing-box.sagernet.org/configuration/shared/v2ray-transport/#websocket).

XHTTP и прежнее имя SplitHTTP распознаются в Xray JSON, URI и ссылках VMess
в Base64. Профиль хранит путь, HTTP authority и режим `auto`, `packet-up`,
`stream-up` или `stream-one`. Shoes использует HTTP/1.1 без TLS, а при TLS
выбирает HTTP/2 по умолчанию или версию по единственному ALPN. `h3` формирует
QUIC-подключение с теми же SNI и проверкой сертификата. REALITY для VLESS
без Vision использует HTTP/2. Несколько ALPN, нестандартные заголовки,
отдельные параметры загрузки и прочие расширения XHTTP отклоняются при импорте.
[Xray XHTTP](https://xtls.github.io/en/config/transports/xhttp.html).

Hysteria2 импортируется из `hysteria2://`, `hy2://` и sing-box JSON, в том
числе из документов в Base64. Профиль хранит один порт, TLS с SNI и опциональный
Salamander. В URI `pinSHA256` закрепляет сертификат сервера по SHA-256, а
`insecure` отдельно управляет проверкой цепочки и имени. В sing-box
`network: "tcp"` отключает передачу пользовательских UDP-датаграмм.
Адаптер передаёт эти профили Shoes через QUIC с ALPN `h3`.
Диапазоны портов, Gecko, ECH, realm, SPKI pins из sing-box и фиксированные
лимиты пропускной способности отклоняются.
[Спецификация URI Hysteria2](https://v2.hysteria.network/docs/developers/URI-Scheme/),
[sing-box Hysteria2](https://sing-box.sagernet.org/configuration/outbound/hysteria2/).

VLESS `encryption` сохраняется из Xray JSON и URI, включая документы в Base64.
Адаптер Shoes проверяет форму настройки до записи каталога и передаёт исходную
строку ядру, сохраняя порядок ключей и блоков padding. Начальная проверка
криптографического материала и установление соединения принадлежат Shoes.
При включённом `encryption` Vision задаётся внутри протокола VLESS. При
`encryption=none` Vision по-прежнему требует TCP с TLS или REALITY. Каталоги
без нового поля читаются в прежнем режиме. [Формат Xray VLESS](https://xtls.github.io/en/config/outbounds/vless.html),
[контракт Shoes](https://github.com/ArthurKoba/BlazeCore/blob/cce97a2c4c1c3bd0a07807f37a7caf3876c79110/docs/src/content/docs/protocols/vless-encryption.md).

Закреплённый Shoes принимает для VLESS и VMess UUIDv4 варианта RFC 4122.
Адаптер проверяет это при импорте до изменения каталога. Текстовые
идентификаторы Xray преобразуются в UUIDv5 по формату Xray. Их поддержка
требует версии Shoes, принимающей UUIDv5.
[Спецификация Xray UUID](https://github.com/XTLS/Xray-core/issues/158),
[валидатор закреплённого Shoes](https://github.com/ArthurKoba/BlazeCore/blob/cce97a2c4c1c3bd0a07807f37a7caf3876c79110/src/uuid_util.rs).

Для прямого ответа `200` от основного URL клиент может сохранить `ETag` в
зашифрованном каталоге вместе с проверенными профилями. Следующий GET к тому же
URL передаёт `If-None-Match`. При ответе `304` сценарий обновляет время последней
успешной проверки и сохраняет профили, выбор пользователя и политику Happ.
Метка не передаётся при редиректе или резервном запросе. Смена основного URL,
успешное обновление с резервного адреса или удаление профиля из подписки
сбрасывают метку. Ответы с `Cache-Control: no-store` или `Vary: *` обходятся
без сохранения метки. [Условные запросы HTTP](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-none-match).

Обновление может использовать один ранее сохранённый резервный URL при сбое
сети, таймауте или подходящем ответе HTTP. Последний рабочий набор профилей
остаётся в каталоге при неполучении валидной замены. Смена домена и новый
резервный адрес на другом origin из метаданных создают запрос на подтверждение.
UI получает origin и одноразовый nonce. Применение требует актуального nonce
и атомарного сохранения. Резервный ответ не может изменить адреса или политику
основной подписки. Полный успешный ответ основного адреса заменяет набор
метаданных. Ответ 304, сбой и успешный запрос к резервному адресу сохраняют
последние метаданные основного адреса. Настройки действуют в пределах своей
подписки и доступны без Happ Provider ID. `hide-settings` скрывает сведения
о её профилях. [Документация Happ](https://www.happ.su/main/dev-docs/app-management).

Desktop и открытый Android-клиент ждут ближайшего срока на общем backend worker.
`profile-update-interval` задаёт положительное целое число часов от последней
успешной загрузки. При старте процесса просроченная подписка ставится в очередь;
`subscription-auto-update-open-enable` добавляет одно обновление этой подписки
на запуск. Директива `subscription-auto-update-enable` хранится как
метаданные и не меняет глобальные пользовательские настройки.

Application вычисляет сроки по состоянию подписок и полученным значениям
времени. Backend читает системные часы, ждёт ближайшего срока и запускает
общий сценарий проверки и атомарного обновления.
Ручные команды прерывают фоновый запрос. Прерванное автообновление остаётся
запланированным и может продолжиться после обработки ручных команд.
Подписка активного соединения ждёт отключения. При сбое автообновления
подписки с заданным интервалом клиент сохраняет рабочие профили и отметку сбоя
в зашифрованном каталоге. Отсрочка действует и после перезапуска клиента, в том
числе при обновлении на открытии. Ручное обновление доступно сразу, успешное
обновление снимает отсрочку. Ошибка видна в состоянии подписки до перезапуска.
Android передаёт ближайший срок системному `JobScheduler`.
Задача ОС использует отдельный `RefreshControl` для запуска и отмены пакетного
обновления. Она вызывает те же сценарии `ClientApplication` и обрабатывает
подписки, срок которых наступил. Правила обновления при открытии активируются
при старте Activity. Платформенное расписание и завершение системного задания
публикуются через `RefreshStatus`. `ClientSession` задаёт общий контракт для
Android, desktop и headless. Headless-команды выполняются в ручном режиме.

Небольшой protocol enum — словарь model contract, не feature matrix поддержки.
Реальная нормализованная схема расширяется под fixtures и версионированный
core contract, с отказом от неподдержанных полей без silent drop.

## Собственное модифицированное ядро

Источник ядра — [ArthurKoba/BlazeCore](https://github.com/ArthurKoba/BlazeCore),
его [архитектура](https://github.com/ArthurKoba/BlazeCore/blob/master/docs/architecture.md)
владеет engine runtime/Device/Session и core/app contract. Не копировать его
schema в клиент. Windows-адаптер проверяет известный артефакт Shoes,
преобразует поддерживаемый профиль в приватную конфигурацию и управляет
дочерним процессом. В режиме `LocalProxy` он публикует loopback-адрес.
В текущей Windows-сборке `Tun` подключает Wintun через переходной адаптер
с loopback SOCKS5 и управляет принадлежащими клиенту системными маршрутами.
Цель — один режим TUN, реализованный в собственном ядре Shoes, будущее
название — Blazecore. Core определяет поведение туннеля и возможности
маршрутизации, платформенный слой предоставляет системный интерфейс.
Blazer использует конфигурацию активного ядра и показывает его возможности
через единый контракт.

Application обращается к движку через `ClientEnginePort`. Проверка системного
туннеля требует передачи данных через интерфейс ОС и проверки его очистки.
Статус этих проверок для каждой системы хранится в [платформенном контракте](platforms.md).

## Нативный GUI и ресурсы

Сохраняем [egui/eframe](https://docs.rs/eframe/0.37.0/eframe/) + Glow:
Rust UI без JS, Electron и WebView, уже проверяемый Windows build.
Iced — подходящая native Rust модель messages/tasks, но смена toolkit сейчас
не даёт доказанной экономии. Slint добавляет отдельный UI DSL и требует
своей проверки лицензии/platform delivery. Оба остаются альтернативами,
не установленными зависимостями.

Toolkit — внешняя деталь; core/application/backend не зависят от layout.
Desktop выбор не доказывает Android/iOS GUI. Headless предназначен для будущего
OpenWrt/router deployment, но target/ABI/libc и runtime ещё не приняты.
Ресурсы измеряются по [performance contract](performance.md); Rust сам по себе
не доказывает энергоэффективность.

## OpenTelemetry и диагностика

Общий backend использует OpenTelemetry 0.33.1 для трейсов, метрик и
структурированных событий. Текущая сборка не задаёт адрес и токен.
В «Настройки → Телеметрия» можно отключить отправку или настроить её вручную.
Ручное сохранение отправляет в `/v1/logs` пустой OTLP/HTTP protobuf-запрос
с таймаутом 1,5 секунды. Только после подтверждения коллектора новый URL и
необязательный Bearer-токен сохраняются в защищённом каталоге и используются
для новых событий. При ошибке продолжают действовать предыдущие настройки.
Экран получает признак сохранённого токена.
Пустое поле сохраняет токен для прежнего URL. При смене URL введите токен
нового коллектора или оставьте поле пустым для запроса без авторизации.

Для развёртывания укажите базовый URL в `OTEL_ENDPOINT` и при
необходимости сырой токен в `OTEL_BEARER_TOKEN`. Blazer сам формирует
`Authorization: Bearer …`. Приоритет имеет `OTEL_ENDPOINT` процесса.
Затем учитываются стандартные параметры SDK `OTEL_EXPORTER_OTLP_*` со своими
заголовками. Последний вариант — значение `OTEL_ENDPOINT` при компиляции,
если оно задано. Для него токен можно передать процессу при запуске.
Токен в артефакт сборки не включается. Ручной режим задаёт URL и Bearer
из настроек Blazer. Явное отключение в приложении имеет приоритет над
параметрами среды и сборки. [Контракт Services Deployment](https://github.com/ArthurKoba/ai-agent-workflow/blob/main/skills/services-deployment/telemetry-variables.md)
Общий адрес `http://127.0.0.1:4318` направит OTLP/HTTP protobuf в
`/v1/traces`, `/v1/metrics` и `/v1/logs`. Для удалённого коллектора с
авторизацией задайте HTTPS-адрес. `OTEL_SDK_DISABLED=true` отключает
экспорт при следующем запуске независимо от выбранного режима.
Формат путей соответствует [спецификации OTLP](https://opentelemetry.io/docs/specs/otel/protocol/exporter/).

На стороне коллектора видны статические `service.name` и `service.version`,
категория операции, её результат, время и служебные идентификаторы SDK.
Метрики `blazer.client.events`, `blazer.client.operation.duration` и
`blazer.client.diagnostic.events.dropped` описывают события клиента, длительность
операций в секундах и вытеснение записей из локального буфера. URL и токены
подписок, имена и адреса профилей, HWID, детали HTTP-ответа и сетевой трафик
в экспорт не входят. Полные снимки состояния остаются внутри клиента.

SDK отправляет ограниченные пакеты на фоновых потоках. Сбой коллектора
не меняет операции VPN. При завершении backend сначала освобождает ресурсы
подключения, затем завершает экспорт. Диагностика в окне получает до
128 последних событий из локального буфера. Headless показывает
`telemetry_export=configured` при настроенном экспорте и
`telemetry_export=not_configured` при отключённом. Доступность коллектора
проверяется по приёму сигналов.
