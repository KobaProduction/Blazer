# Требования к VPN-клиенту и границы системы

Этот документ фиксирует целевой продукт по решению владельца от 11 ноября
2026 года. Требование здесь не означает реализованную функцию. Фактические
возможности определяются исходниками и проверками конкретной версии; текущая
Windows GUI-заготовка не доказывает готовность VPN или других платформ.

Название продукта пока не выбрано: «VPN-клиент», техническое имя `vpn-client`.
Цель — открытый нативный Rust-клиент с собственным модифицированным Shoes,
простым знакомым управлением и измеримо экономным использованием ресурсов.
Приватный репозиторий сейчас служит подготовке; открытая публикация — отдельное
решение владельца. Собственный код предназначается для MIT. Это не меняет
лицензий зависимостей, upstream и заимствованных компонентов.

## Обязательные принципы

- Rust и нативный GUI. JavaScript, Electron и WebView не используются для UI
  или исполнения продукта. Документационные сайты зависимостей не являются UI.
- Память, CPU, энергия, wakeups и лишний трафик — критерии каждой функции.
  Сам язык Rust не является доказательством экономичности.
- GUI — внешний адаптер. Подписками, профилями и lifecycle можно управлять
  без окна и без загрузки GUI-зависимостей в headless-артефакт.
- Зависимости направлены внутрь по Clean Architecture. Импорт, storage,
  telemetry, OS API и engine implementations отделены от домена и сценариев.
- Поведение UI и системной сети отражает подтверждённое состояние.
  Живой процесс ядра не равен работающему маршруту или VPN-подключению.
- Референс — сценарии Happ, а не его закрытый код, ресурсы, ключи или брендинг.
  Цель полного функционального соответствия доказывается матрицей, а не названием.
- Настройки, которые пока не поддерживает платформа или ядро, показываются
  как недоступные с причиной. Не применять скрытую подмену протокола или маршрута.

## Система и платформы

| Компонент | Обязанности продукта |
| --- | --- |
| Native GUI | Главная кнопка, серверы, подписки, профили, routing/VPN/diagnostics, понятные ошибки |
| Client application/backend | Валидация входа, сценарии, сохранение состояния, работа без GUI, orchestration ядра |
| Core adapter | Преобразование typed model в согласованный engine contract, capabilities, запуск/остановка/состояние |
| Модифицированный Shoes | Сетевой runtime, протоколы и серверные функции по контрактам владельца ядра |
| Platform adapters | Системный VPN/proxy, DNS/routes, permissions, lifecycle и защищённое хранение |
| Telemetry facade | Обязательная OTel instrumentation, локальная диагностика и управляемый экспорт |
| Будущие внешние сервисы | Device/session control и добровольный обмен результатами стратегий; серверы ещё не реализованы |

Первая цель — Windows x64 MSVC. Linux и macOS, Android и iOS, телефоны и
планшеты — целевые платформы дальнейшей разработки. OpenWrt/роутеры получают
headless client/backend без GUI. Архитектура и размеры интерфейса учитывают
touch, клавиатуру и масштабирование; один desktop toolkit не доказывает
готовность мобильной оболочки.

Каждая платформа принимается отдельно: target/ABI/libc, build, запуск,
permissions, жизненный цикл, сетевой data path и ресурсы на реальном устройстве.
Текущая база Shoes ограничивает TUN/WireGuard Unix-ветками; Windows GUI build
не является доказательством Windows VPN. Точный статус принадлежит core platforms.

## Функциональные требования и приёмка

Все строки — целевые обязательства. Исключения из полного пользовательского
объёма требуют явного решения владельца; отсутствие engine capability не скрывает
требование, а остаётся видимым ограничением приёмки.

| ID | Требование | Проверяемый критерий |
| --- | --- | --- |
| C01 | Знакомый главный экран: одна основная кнопка, активный профиль/сервер, статус и ошибка | Сценарии первого запуска, выбора, подключения, отмены, отключения и отказа; повторное нажатие не создаёт второй runtime |
| C02 | Подписки: добавить, просмотреть, обновить, изменить, удалить; ручные конфиги | Изменения сохраняются после перезапуска; невалидное обновление сохраняет последнюю рабочую версию |
| C03 | Импорт URL, текста/буфера, файлов, QR и deep links как в референсе | Для каждого заявленного формата есть versioned fixture и malformed-input проверки; импорт не запускает соединение автоматически |
| C04 | Совместимость с подписками и конфигурациями экосистемы Happ/Xray | Поддержанные поля проходят parse → нормализация → typed model → core adapter; неподдержанное явно диагностируется без silent drop |
| C05 | Понятные профили и управление серверами | Выбор, редактирование, группировка/порядок и операции из matrix воспроизводимы; удаление не повреждает другой профиль |
| C06 | Routing и DNS, правила direct/proxy/block, geo-источники и исключения | Валидация ссылок/порядка/приоритетов до применения; пользователь видит текущую и ожидающую применения версии |
| C07 | Настройки VPN/proxy/TUN, autostart/reconnect и platform options | Проверяются только поддержанные capabilities; отмена/сбой очищают принадлежащие приложению изменения routes/DNS |
| C08 | Логи и диагностика, выбор уровня и просмотр состояния | Ограниченное хранение; доступен понятный отказ engine/platform; диагностический export очищает секреты |
| C09 | Проверка серверов и текущего соединения | Тип пробы и timeout видны; отмена и лимиты параллелизма работают; задержка не выдаётся за bandwidth |
| C10 | Экспорт/перенос поддержанных пользовательских конфигов | Round-trip fixtures сохраняют смысл; предупреждение перед раскрытием секретов; закрытые provider-specific форматы не объявляются совместимыми без проверки |
| C11 | Backend работает независимо от GUI | Headless build не тянет eframe/оконные библиотеки; те же application-сценарии проверены отдельным entrypoint |
| C12 | Общение GUI/backend/core типизировано и отменяемо | Команды, версии, ошибки и события имеют контракт; offline/stale state/перезапуск backend не зависают в UI |
| C13 | Локальное состояние и storage изолированы портом | Атомарное обновление, migration/recovery и secret storage проверены до принятия persistence; SQLite/ORM — кандидаты, не заранее доказанная необходимость |
| C14 | Функциональная полнота референса | Каждое действие выбранной Happ-версии внесено в matrix и имеет scenario result либо согласованное платформенное исключение |
| C15 | Настройки энергоэффективности | Ограничения фоновой работы, probes, очередей, таймеров и telemetry видимы и проверены по resource profile |
| C16 | Расширяемость и будущая персонализация | Предметные сценарии не зависят от layout/темы; новые оболочки и настройки не дублируют бизнес-логику |

Xray — форматная экосистема совместимости, а не выбранный engine.
Нельзя передать произвольный Xray JSON в Shoes и объявить задачу решённой.
Импорт Xray JSON и экспорт в Xray-совместимый формат — отдельные направления
адаптеров с проверяемой поддержкой полей. Engine-конфигурация формируется только
по согласованному контракту модифицированного Shoes.

Обычные подписки и protocol URI, provider metadata, криптоссылки Happ,
ограниченные/HWID-ссылки и шифрованное содержимое имеют разные compatibility
границы. Для каждого формата требуется доступная спецификация либо разрешённый
проверочный fixture. Неизвестный формат не отправляется стороннему decrypt API
и не объявляется поддержанным. Нужны решения владельца формата для закрытых
механизмов; никакие закрытые ключи приложения не извлекаются.

## Ресурсы и доказательство эффективности

Обязателен воспроизводимый baseline отдельно для GUI, backend и core, затем
для полного дерева процессов. До измерений численные пределы RSS, latency,
CPU или батареи не выдумываются. Числа и допустимые регрессии утверждаются
в resource budget по platform profile до функциональной приёмки этого профиля.

| Workload | Что измерить |
| --- | --- |
| Пустой запуск, видимое/скрытое окно, headless idle | Cold/warm start, resident/private memory, peak, CPU time, repaint/wakeups/таймеры |
| Импорт и обновление фиксированного набора подписок/правил | Peak/steady память, allocations, длительность, лишний сетевой обмен, отмена |
| Работа выбранного data path под одинаковым полезным трафиком | Throughput, latency distribution, CPU, память на соединение, энергия на объём полезных данных |
| Потеря сети, смена сети, reconnect и отмена | Время восстановления, backoff, оставшиеся tasks/sockets, расход проб и cleanup |
| OTel выключен/включён, collector недоступен | Overhead, границы очереди и cardinality, drops/backpressure, отсутствие блокировки data path |
| Мобильный background и роутер с ограниченной памятью | Реальная энергия, wakeups/нагрев, OS lifecycle, соответствие профилю памяти/CPU |

Каждый результат хранит hardware/OS/target, версии приложения/ядра/driver,
режим питания, сеть, протокол/криптографию/маршрут, dataset и способ измерения.
Повторяемость и число прогонов определяются baseline-методикой; показываются
распределение и разброс, а не лучший единичный запуск. CPU-прокси не выдаётся
за измеренную энергию. Сравнение с Happ возможно только в одинаковых условиях
с указанием версии и режима. Заявление «эффективнее» принимается по этим данным.

Инварианты: bounded queues/buffers/caches/history; backpressure; cancellation
и timeout долгих операций; отсутствие busy polling и постоянного repaint в idle;
освобождение GUI-ресурсов headless-сборкой; фоновые задачи принадлежат явному
lifecycle. Аппаратное ускорение и программный fallback показываются в диагностике,
а выбор и стоимость конкретного пути принадлежат core/platform authority.

## OpenTelemetry и данные

OTel — обязательная часть целевой архитектуры для traces, metrics и logs.
Core передаёт ограниченные события через versioned boundary; клиент выбирает
локальные sinks и exporters. SDK/формат экспорта остаются во внешнем слое.
Работа VPN не зависит от доступности collector; очереди, sampling, cardinality,
retention и overhead ограничены и измеряются.

По умолчанию сетевой exporter выключен. Включение имеет явные endpoint,
категории данных, preview/redaction и отзыв разрешения. Полезная диагностика
не требует payload, ключей, токенов, URL подписок, destination/SNI или
идентификатора физического устройства. Эти данные не должны утекать в логи,
метрики или crash reports. Отдельно определяются локальные TTL/очистка.

Будущий сервис обмена результатами DPI-стратегий с provider/network metadata,
грубой географией или IP — отдельная функция, а не автоматическое последствие
включения OTel. Нужны минимизация и отдельное согласие; raw IP/геоданные
по умолчанию не собираются и не экспортируются. Правила платформы могут
ограничивать аналитику даже при согласии пользователя; owning contract —
core architecture и исследование platform policy.

## Модули и доверие

Модульность сначала обеспечивается выбором protocol adapters при сборке.
Возможность скачать и подключить внешний модуль без переустановки — целевое
исследование, а не обещанный механизм всех ОС.

Перед любым исполнением внешнего модуля обязательны доверенный корень/издатель,
подпись и digest фактических bytes, manifest version, engine/API/ABI и target
совместимость, разрешённые capabilities, resource policy, key rotation/revocation
и безопасный rollback. Неподписанные, изменённые, отозванные, несовместимые или
пониженные вопреки policy версии отклоняются fail closed. Подпись подтверждает
происхождение, но не заменяет изоляцию и ограничение полномочий.

Приёмка включает отрицательные fixtures: tampering, чужой key, revoked key,
несовместимый target/ABI, partial download и отказ активации с сохранением
рабочей версии. Loader/downloader/hot reload сейчас не считаются реализованными.

На iOS исходная модель — native code внутри подписанного bundle. Apple
ограничивает downloaded executable code, меняющий функции приложения.
Для Google Play произвольная загрузка native `.so` вне Play также ограничена.
Поэтому «подписан» не означает «разрешён магазином»; desktop delivery,
store-managed Android delivery и iOS обновление принимаются отдельно по
[Apple 2.5.2](https://developer.apple.com/app-store/review/guidelines/#software-requirements)
и [Google Play policy](https://support.google.com/googleplay/android-developer/answer/16559646).
Wasm/скрипт не является заранее разрешённым обходом этих ограничений.

## Приёмка текущего развития

Текущий срез развивает foundation: durable требования, UI/backend boundary,
типизированные порты и локальные проверки. Он не обещает сразу весь VPN или
полный Happ parity. Функциональные критерии C01–C16 сохраняются целевыми.

Проверки локальные: во время разработки — затронутые области, после стабилизации
— один полный финальный gate. CI не используется как критерий текущей разработки.
Source/build/runtime/interop/performance evidence различаются. Для принятия
рабочего VPN обязательны реальный data path, lifecycle/cleanup и ресурсный
baseline на заявленной платформе; зелёная сборка или макет этого не заменяют.
