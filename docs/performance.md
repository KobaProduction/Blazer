# Измерение ресурсов

Память, CPU, энергия и лишний сетевой обмен — самостоятельные критерии
[продукта](product-requirements.md#ресурсы-и-доказательство-эффективности).
Этот документ владеет методикой baseline. Он не вводит численные performance
budgets до измерений и не объявляет Rust или выбранный GUI экономичнее Happ.

## Локальный idle probe

`scripts/measure-idle.ps1` измеряет только явно выбранный наш Windows EXE.
Он не собирает приложение и не запускает тесты. Обязательный expected SHA256
связывает запуск с проверенным артефактом. Скрипт делает отдельную копию в
указанный output directory, сверяет hash и запускает именно её, чтобы не держать
оригинальный build output во время relink.

Запуск запрашивает `WindowStyle Hidden`; это workload **hidden-idle-requested**,
а не проверка видимого GUI или его UX. Реальная видимость окна инструментом
не подтверждается. Никаких нажатий подключения или изменений VPN/routes/DNS
скрипт не делает. Он наблюдает только собственный PID и завершает только
процесс с совпадающими copy path и start time. При недоступных метриках выдаёт
UNVERIFIED, при ошибке прекращается с ненулевым кодом.

После отдельного warmup измеряются wall time, CPU time delta, CPU как доля
одного логического ядра, Private Bytes и Working Set. Peak в отчёте означает
максимум среди samples, а не гарантированный process lifetime peak.
CPU-проценты могут превышать 100 при многопоточной работе.
Это **не** измерение батареи, wakeups, allocations, throughput или энергии.

Пример одного измерения; SHA256 нужно брать от конкретной проверенной сборки:

```powershell
cd C:\Users\Koba\VPN\Blazer
$binaryHash = (Get-FileHash -LiteralPath 'C:\path\to\vpn-client.exe' -Algorithm SHA256).Hash
pwsh -NoProfile -File scripts/measure-idle.ps1 -ExecutablePath 'C:\path\to\vpn-client.exe' -ExpectedSha256 $binaryHash -OutputDirectory 'C:\path\to\work\performance' -SourceRelation 'exact build/source relation'
```

Duration/warmup/sample interval — параметры workload, а не нормы приемлемого
потребления. Измерение не сравнивает Happ, не читает другие процессы и не
собирает трафик. Raw report и проверенная копия остаются локально в output
directory; их нельзя автоматически превращать в публичную диагностику.

## Воспроизводимый продуктовый baseline

Для каждого будущего platform profile фиксируются target/ABI, OS и hardware,
режим питания, source/build identity приложения и ядра, build flags, dataset,
workload и способ измерения. GUI visible, GUI hidden и headless backend
измеряются раздельно; потом — весь наш process tree. Сравнение старого и нового
артефактов требует одинаковых условий и повторяемых прогонов.

Помимо idle нужны контролируемые import/refresh, connect/disconnect/cancel,
steady data path, network loss/reconnect и отказ telemetry exporter. Эти
сценарии выполняются только после появления соответствующего проверенного
backend и отдельного разрешённого стенда. Mobile background и OpenWrt требуют
реального устройства, а не переноса desktop-результата.

До заявлений об энергоэффективности нужны реальные platform power measurements
и одинаковый полезный workload. CPU time — полезный вспомогательный сигнал,
но не замена энергии. Число повторов, длительность, статистика и численные
бюджеты утверждаются после пилотного baseline. Результат одного короткого
idle probe — наблюдение о конкретном binary, не performance verdict продукта.

## Полученные результаты

### Запуск headless и подключение Shoes на Windows

На одном Windows-хосте сравнили по три запуска двух debug-сборок на одинаковой
loopback-нагрузке. Использовался один проверенный бинарник Shoes размером
49 314 304 байта. Время измеряли с запуска процесса до объявления готового
прокси и с EOF на stdin до выхода. Порт освобождался и приватный каталог ядра
очищался во всех прогонах.

| Показатель | До настройки `sha2` | После настройки `sha2` |
| --- | --- | --- |
| Запуск до готовности | 4,168 / 3,694 / 3,508 с | 0,789 / 0,813 / 0,922 с |
| Медиана запуска | 3,694 с | 0,813 с |
| Медиана штатного выхода | 54,51 мс | 48,18 мс |

Для `sha2` в профиле `dev` установлен `opt-level = 3`. Отдельный эксперимент с
одинаковым файлом и циклом чтения подтвердил, что SHA-256 совпадает, а время
хеширования снизилось с 3,1–3,6 с до 0,12–0,14 с. Контроль ACL, версии и хеша
остался на пути запуска. Headless-сборки также различались правками backend,
поэтому сравнение полного приложения не изолирует вклад `sha2`. Результаты
относятся к локальным debug-сборкам; ускорение release этим опытом не измерялось.

### Отложенная инициализация HTTP при запуске

Windows x86_64, 15 ноября 2026 года, `vpn-headless status` из двух debug-сборок
до подключения зависимостей Windows TUN. В обеих сборках пустой тестовый каталог,
один и тот же путь к отсутствующему Shoes и одинаковые параметры запуска без
окна. После трёх прогревов каждого варианта выполнено по 25 запусков с
чередующимся порядком в парах. Измерялось время от старта процесса до выхода.

| Вариант | Медиана | P90 |
| --- | ---: | ---: |
| HTTP-клиент и Tokio при открытии каталога | 73,20 мс | 79,27 мс |
| HTTP-клиент и Tokio при первом сетевом запросе | 66,73 мс | 83,86 мс |

Медиана сократилась на 6,47 мс (8,8%), P90 в этой выборке вырос на 4,59 мс.
Замер не оценивает задержку первого HTTP-запроса, GUI и энергопотребление.

### Ожидание готовности локального прокси на Windows

15 ноября 2026 года на одном Windows x86_64 сравнили две release-сборки
`vpn-headless proxy` с одним и тем же зашифрованным локальным каталогом и
закреплённым Shoes. После трёх прогревов каждого варианта выполнили 20 пар
со сменой порядка в соседних парах. Граница замера проходила от запуска
headless до первой строки с готовым SOCKS5-адресом.

| Вариант ожидания | Медиана | P90 |
| --- | ---: | ---: |
| Проверка по таймеру | 799,80 мс | 917,12 мс |
| События Windows и сигнал готовности Shoes | 712,71 мс | 863,89 мс |

Разница медиан составила 87,09 мс (10,9%), медиана разниц внутри пар — 58,14 мс.
Новая сборка была быстрее в 19 из 20 пар.
Во всех прогонах EOF приводил к штатному выходу и освобождению приватного каталога.
На пути запуска остались ACL, SHA-256, проверка версии и конфигурации, а также
SOCKS5-проба. Этот замер ограничен готовностью локального прокси Windows headless.

Для запуска Shoes в Job Object провели отдельный замер `vpn-headless proxy` на
том же Windows x86_64. После двух прогревов каждого варианта выполнили 12 пар
с чередующимся порядком. Обе release-сборки использовали один каталог и ядро.
Медиана готовности выросла с 545,98 до 552,83 мс, P90 с 937,52 до 957,17 мс.
Медиана разниц внутри пар составила +18,75 мс. Замер относится к локальному
прокси, энергетические показатели отдельно не измерялись.

Отдельно сравнили подготовку приватного каталога через `whoami` и `icacls`
с вызовами Windows API. В обеих release-сборках Shoes запускался в Job Object.
После двух прогревов каждого варианта выполнили 12 пар с чередующимся порядком
и измерили время от запуска headless до первой строки с готовым адресом SOCKS5.
Медиана снизилась с 732,61 до 595,98 мс, P90 с 1 207,99 до 884,19 мс.
Медиана разниц внутри пар составила −111,57 мс. Вариант с Windows API оказался
быстрее в 10 из 12 пар. Данные относятся к локальному прокси на одном хосте.

### Загрузка Shoes при первом подключении на Android

Эмулятор Android API 35 x86_64 на одном Windows-хосте. Две локальные APK с
одной сборкой Shoes и пустым каталогом измерены в порядке A/B/B/A. В каждом
блоке один прогрев и пять замеров в заново запущенном процессе. Таймер начинался
перед открытием Activity и останавливался после получения готового состояния
backend. PSS измерялся сразу после этого. P90 рассчитан методом ближайшего ранга.

| Показатель | Shoes при открытии сессии | Shoes при первом подключении |
| --- | ---: | ---: |
| Медиана до готовности | 2,843 с | 2,564 с |
| P90 до готовности | 3,862 с | 2,901 с |
| Медиана PSS | 39,79 МиБ | 30,01 МиБ |

В новой сборке интерфейс предлагал TUN, а `libshoes.so` отсутствовала в
`/proc/self/maps` во всех десяти замерах. APK без Shoes открылся с недоступным
TUN. Эксперимент ограничен этим эмулятором и пустым каталогом. Задержка первого
подключения, ARM64 и энергопотребление отдельно не измерялись.

Счётчик CPU вырос в первом интервале после warmup, затем не менялся на

hardware/power условий, измеренного observer overhead и статистики повторов.
Wall time loop и timestamps samples включают несколько разные границы сбора;
цифры не следует трактовать как точный steady-idle regression threshold.

Результат подтверждает доступность измерения собственного процесса, но не
видимый GUI, качество VPN, эффективность батареи или превосходство над Happ.
Численные продуктовые бюджеты по этому одному запуску не установлены.
