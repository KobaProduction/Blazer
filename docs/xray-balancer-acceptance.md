Первичная приёмка маршрутизации и нативных групп выполнена 20 ноября 2026 года.
Round Robin и leastPing через упакованный клиент проверены повторно
22 ноября 2026 года на Windows с поставляемым BlazeCore
`0.3.7+gb90121c0406c`. Проверка нативного контракта сверяет SHA-256 и версию
с закреплёнными значениями Blazer. Исходники BlazeCore не изменялись.
Проверенный `dist/windows/client/blazer.exe` имел SHA-256
`46386E894D081ED15AE59BDD9DDCABAC07B991629D3B91638FF975D7409334E1`.
На финальном пакете с SHA-256
`DB5419BF28B0068FE21DE6F2B03B3A509023844A03B2AD8E28B47684B233A737`
отдельно прошли последовательное наблюдение, переключение A → B при отказе
и проверка завершения процесса со всеми его публичными и служебными портами.

## Что работает в клиенте

Реальный тест `routing_commands_drive_localproxy_dns_and_first_match` прошёл
через CLI, ядро клиента и закреплённый процесс BlazeCore. Проверены:

- блокировка по точному домену до обращения к DNS и прокси;
- прямой маршрут по доменному суффиксу и TCP DNS;
- CIDR IPv4/IPv6, порядок правил и первое совпадение;
- выбранный прокси и маршрут по умолчанию;
- остановка клиента с освобождением локального порта.

Эта проверка подтверждает собственные правила Blazer `Domain`, `DomainSuffix`,
`Cidr` и действия `Proxy`, `Direct`, `Block`. Она не подтверждает применение
произвольной политики из Xray. Карточки GeoIP/geosite и domain strategy в UI
пока не подключены к исполняемым сценариям; обновление баз недоступно.

## Полный Xray-конфиг: принятый набор

Blazer поддерживает `domainStrategy: AsIs`, явные стратегии `roundRobin`
и `leastPing` в `routing.balancers` и ссылки `balancerTag`, один или ни одного локального
входа SOCKS/HTTP без авторизации. Выходы прокси, direct и block, условия
точного домена, доменного суффикса, CIDR и TCP/UDP сохраняются с порядком
правил. Xray `selector` разворачивается по префиксам тегов в участников
группы. [Официальный формат маршрутизации Xray](https://xtls.github.io/en/config/routing.html).

Граф становится одним профилем с группами и ссылками на выходы. Полный JSON
сохраняется как защищённый исходник для редактора конфигурации. HTTP-подписка,
её Base64-обновление и ручной импорт используют общий контракт и хранилище.
Границы домена, application, инфраструктуры и UI описаны в
[архитектурном контракте](architecture.md#собственное-модифицированное-ядро).
Автоматическая проверка группового профиля проходит через граф движка;
представительный адрес карточки не заменяет её прямым TCP-пингом.

`scripts/test-xray-balancer.py` прошёл на упакованном
`dist/windows/client/blazer.exe` с прежним закреплённым BlazeCore.
Использованы HTTP-сервер подписки, два локальных SOCKS-выхода A/B и
изолированные каталоги. Пользовательские подписки, системный прокси
и маршруты Windows проверка не меняет.

| Сценарий клиента | Наблюдаемый результат |
| --- | --- |
| HTTP-подписка → один граф → DPAPI → новый процесс CLI → LocalProxy | Шесть новых потоков идут строго A B A B A B |
| Открытый поток на A, пока создаются другие потоки | Остаётся на A; новые продолжают чередоваться |
| Правило провайдера block и отдельное правило на B | Блокировка сохраняется; фиксированный маршрут использует B |
| Обновление той же подписки в Base64 | UUID группового профиля сохраняется |
| Глобальные пользовательские block и Proxy-условие поверх графа | Пользовательская блокировка действует; правила провайдера и Round Robin сохраняются |
| Ручной импорт полного JSON → защищённый каталог → новый CLI-процесс | Та же проверка данных, маршрутов и A B A B A B проходит |
| Остановка каждой сессии | Процесс завершается, локальный порт освобождается |

Последовательность с шестью потоками и сохранением открытого соединения
прошла для исходной HTTP-подписки, обновлённой Base64-подписки с
пользовательской политикой и отдельного ручного импорта JSON.

## LeastPing и общая observatory

`scripts/test-xray-leastping.py` прошёл на том же упакованном клиенте.
Синтетические выходы A/B отвечают на HTTP-проверки с задержками 5/150 мс,
отдельный выход C задан глобальным по умолчанию и при необходимости в
`fallbackTag`. Все HTTP-ответы обслуживаются локально через SOCKS-фикстуры;
пользовательские данные и настройки сети ОС не меняются.

| Сценарий leastPing | Наблюдаемый результат |
| --- | --- |
| Ручной JSON → защищённый каталог → новый CLI-процесс | Выбран быстрый живой A |
| Ответ HTTP 503 от ресурса проверки A | A остаётся живым: учитывается получение HTTP-ответа, не его код |
| Последующий отказ проверки A | Новые соединения идут через B; открытый поток остаётся на A |
| Отказ проверки обоих участников | Используется явный fallback C |
| Восстановление проверки A | Новые соединения возвращаются на A |
| HTTP-подписка и её Base64-обновление | Один граф и прежний UUID; те же переключения работают после чтения каталога новым процессом |
| Отсутствующий `fallbackTag`, оба участника недоступны | Используется глобальный выход C, а не первый кандидат A |
| `subjectSelector` проверяет только B | Непроверенный A исключён из выбора и не получает запросов observatory |
| Остановка во время ожидающих HTTP-ответов | Проверки отменяются; сессия завершается менее чем за три секунды |
| Последовательный режим observatory | GET идут A B A B; между началами соседних проверок выдерживается заданная пауза 200 мс с допуском измерения 20 мс |
| Последовательный режим, A перестаёт отвечать | Новый поток переходит с A на B |
| Остановка последовательной сессии | PID движка завершён; все его публичные, управляющий и фиксированные входы проверок исчезли и порты повторно доступны для bind |

Фикстура подтверждает GET для observatory. Чистые доменные тесты отдельно
проверяют исключение устаревшего успешного отчёта после отказа, целые
миллисекунды и разрешение равенства по порядку первого прихода отчётов.
Runtime хранит общий набор отчётов, раскрытый из `subjectSelector`,
и обновляет нативные selector-группы. Round Robin продолжает выполнять
свой порядок A B A B A B: его сквозная проверка повторно прошла после
подключения leastPing.

## Что остаётся неподдержанным

`random`, leastLoad, `burstObservatory`, другие domain strategy,
непустые настройки DNS Xray, несколько входных слушателей и авторизованные
входы не преобразуются в исполняемый граф. Неизвестные поля и условия,
включая regex/geosite, также отклоняются. Это граница текущего адаптера;
стратегии поставляемого ядра не объявляются эквивалентами Xray автоматически.

Прежняя фикстура leastPing с поддержанными fallbackTag и observatory стала
положительной проверкой полного графа. Отрицательные фикстуры продолжают
проверять неизвестные стратегии, отсутствующую observatory, несуществующие
ссылки и неподдержанные поля:

- строгий импорт возвращает `UnsupportedFeature`;
- импорт подписки, включая Base64, создаёт одну неподдерживаемую запись;
- политика не превращается молча в независимые подключаемые серверы;
- соседняя независимая поддерживаемая конфигурация продолжает импортироваться.

Неподдерживаемая запись не хранит полный JSON графа для редактора;
повторный импорт требует исходной конфигурации или обновления подписки.
Поддержанный граф сохраняет исходник целиком.

## Возможности поставляемого BlazeCore

`scripts/probe-balancer-contract.py` проверил нативный граф реальным трафиком
через два локальных SOCKS-сервера, без изменения системных маршрутов или прокси:

| Сценарий | Наблюдаемый результат |
| --- | --- |
| Упорядоченные domain/suffix/CIDR/block-правила | Первое совпадение и нужный выход |
| Round-robin, шесть отдельных соединений | 3:3 между двумя выходами |
| Взвешенный выбор повторением членов | 4:2 между двумя выходами |
| Selector и изменение через controller | Новые соединения используют новый выбор; открытое сохраняет прежний |
| Недоступный член round-robin | Ошибка без повторной отправки пользовательских данных другому члену |
| URL-test, отказ проверки быстрого выхода | Выбор переходит на другой здоровый выход |

Нативные типы групп: `round-robin`, `selector`, `url-test`.
Xray `selector` в балансировщике — фильтр по префиксам тегов выходов;
нативный `selector` BlazeCore — ручной выбор участника. Эти понятия нельзя
переносить друг в друга по совпадению имени.
Имена `random`, `fallback`, `failover`, `leastPing`, `leastLoad` нативный
валидатор отвергает. `url-test` нельзя автоматически объявлять точным
эквивалентом Xray leastPing/observatory: нужны явные правила преобразования.
HTTP-ответы проверок здоровья в фикстуре обслуживаются локально;
для публичного имени ресурса может использоваться системный DNS.

Разбор leastPing выявил различия: при отказе всех участников нативный
`url-test` оставляет действующего либо первого участника; Xray leastPing
использует `fallbackTag` или глобальный выход по умолчанию. Observatory
проверяет GET, нативная проверка — HEAD; отличаются общий `subjectSelector`
и расписание. Поэтому leastPing реализован общим наблюдателем процесса
клиента поверх нативных selector-групп, с собственной доменной политикой
выбора. Клиентские JNI/Packet Tunnel-адаптеры
подключают общий Rust-наблюдатель через selector API; без соответствующей
capability проверенной библиотеки запуск отклоняется. Поставка и приёмка
нового API отслеживаются [отдельным контрактом](core-selector-ffi-request.md).
Поддержка Round Robin не включает автоматическое переключение по состоянию
здоровья или fallbackTag.

## Android: подтверждённый TUN и JNI

22 ноября 2026 года `scripts/test-android-leastping.py` прошёл на Android 15
x86_64 в изолированном AVD `Blazer_API_35`. Использована обычная проверка
доверия сборщика и библиотека из финального набора `mobile-selector`:

- исходный commit `10512be664e2100bb4a0ad3bb95f6c70a184ee2d`,
  tree `ef9a083e67fe74e044e65735cff471c58e902f4b`;
- JNI-версия `0.3.7`, selector capability bit 0;
- SHA-256 `064DA9243AD53DEB60C1AC464EDF2724118EA6AF5E957E6CBE7B9611E85E170A`.

В том же доверенном наборе библиотека `arm64-v8a` имеет SHA-256
`03470F1976B1286ECF7DFC4FB33BBF24272B29052965D8DEA5282FFFEE443298`.
Проверены совпадение source tree и JNI-версии, ELF64 AArch64, selector-экспорты
C/JNI и выравнивание LOAD 16 КиБ. Сетевой тест на ARM64-устройстве не выполнялся.

Проверка использует настоящий `VpnService`, JNI и общий Rust-наблюдатель;
локальные SOCKS-фикстуры доступны через `adb reverse`. Данные проходят через
Android TUN. Подтверждены GET-проверки обоих участников, выбор A → B → fallback C
→ A при отказе и восстановлении, сохранение открытого потока на A, остановка,
новый уникальный handle после повторного старта и отказ устаревшего handle.
Это результат финального артефакта; ранний диагностический прогон его не заменяет.
Физическое ARM64-устройство и Apple Packet Tunnel этим прогоном не проверяются.

Отдельные регрессионные тесты Android-валидатора подтверждают, что граф с
расширенными XHTTP metadata/packet wire и Native VLESS/WireGuard проходит общий
строгий валидатор и сохраняет параметры в TUN-конфигурации. Прежние платформенные
запреты удалены после обновления закреплённого ядра. Это проверка преобразования,
а не сетевой прогон XHTTP или WireGuard: описанная выше Android-приёмка использует SOCKS-выходы.

Обычный универсальный APK `target/android/blazer-debug.apk` собран и подписан
без `-Acceptance`, включает обе ABI и последние исправления Android-валидатора.
Размер — 35 292 060 байт, SHA-256:
`09E6A6FE49182849208DC11E2A3E37029B61C4823D14A11FF399CEB3271D6560`.
В manifest нет instrumentation, в DEX нет `AcceptanceInstrumentation`,
в клиентской ELF каждой ABI нет `AcceptanceBridge`; вложенные библиотеки ядра
имеют указанные выше SHA-256, ELF64-архитектуры соответствуют ABI.
Проверены APK-подписи v2/v3/v4. Тестовые входы не попадают в обычную поставку.

## Границы подтверждения

Результат клиентской приёмки относится к указанному набору Xray Round Robin
и leastPing в Windows LocalProxy и к leastPing в Android TUN x86_64.
Созданная нативная конфигурация управляемого Windows TUN
прошла проверку ядром; фактическая передача данных этого графа через TUN
Windows не проверялась.
Сохранение полного исходного JSON подтверждено тестами импорта и хранилища;
сквозной сценарий изменения графа через GUI-редактор не проходил приёмку.

Для Apple-моста 22 ноября прошли Rust `cargo check` под `aarch64-apple-ios`,
генерация C-заголовка, проверка границ слоёв и тест владения конфигурацией,
handle и остановки наблюдателя на Windows. Это не сборка Swift-расширения
и не запуск на iPhone. Для них требуется Mac с Xcode и подписанная поставка
совместимой библиотеки BlazeCore. Android-код клиента прошёл Rust-проверку
ARM64; этот compile-check не заменяет сетевой тест на ARM64-устройстве.

Отказ участника, URL-test и ручное переключение selector в таблице выше
проверены на нативном контракте BlazeCore. Они не доказывают импорт и
применение соответствующих стратегий Xray в Blazer. Для каждого нового
преобразования нужны сохранение полного графа, явная семантика правил и
сетевая проверка цепочки подписка → каталог → новый процесс → данные.
